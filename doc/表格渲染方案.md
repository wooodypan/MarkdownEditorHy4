表格和图片本质上是同一类问题——"需要用真正的视图渲染，而不是靠 attribute 装饰纯文本就能表达"，所以架构上应该复用图片那条路径（`NSTextAttachmentViewProvider`），而不是想办法用 `NSAttributedString` 的表格能力（`NSTextTable`，那是给 TextKit 1 富文本用的，样式能力弱、也没法放交互控件，不建议用）。

## 结论先行

**表格整体做成一个 `NSTextAttachment`，附件里内嵌一个轻量自绘表格 view，插入在原始表格源码文字的上方；下方保留原始 `| a | b |` 这种源码文字并弱化显示。** 这跟你现有的图片方案是同一套机制，只是附件里塞的 view 从 `UIImageView` 换成一个表格 view。

## 具体设计

### 1. 渲染阶段：`visitTable`

```swift
mutating func visitTable(_ table: Table) -> NSAttributedString {
    // 1. 原始表格源码文字，全部保留、弱化显示（与图片语法处理方式一致）
    let markdownText = literalText(for: table)   // 从 sourceSlice 精确切出整块表格源码
    let dimmedText = NSAttributedString(string: markdownText, attributes: [
        .font: theme.typography.codeFont,   // 表格源码用等宽字体更利于对齐阅读
        .foregroundColor: theme.colors.syntaxMarkerDimmed,
    ])

    // 2. 解析出结构化数据，供表格 view 使用
    let tableData = MarkdownTableData(
        columnAlignments: table.columnAlignments,  // swift-markdown 的 Table.ColumnAlignment
        header: table.head.cells.map { $0.plainText },
        rows: table.body.rows.map { row in row.cells.map { $0.plainText } }
    )

    let attachment = MarkdownTableAttachment(data: tableData, theme: theme)
    let attachmentString = NSMutableAttributedString(attachment: attachment)
    attachmentString.addAttribute(.paragraphStyle,
        value: theme.paragraphStyle(for: .tableAttachmentBlock),
        range: NSRange(location: 0, length: attachmentString.length))
    attachmentString.addAttribute(.markdownSynthetic, value: true,
        range: NSRange(location: 0, length: attachmentString.length))

    let result = NSMutableAttributedString()
    result.append(attachmentString)
    result.append(NSAttributedString(string: "\n", attributes: [.markdownSynthetic: true]))
    result.append(dimmedText)
    return result
}
```

这和 `visitImage` 几乎是镜像结构：附件在上、`markdownSynthetic` 标记换行、弱化源码文字在下——复制拦截（`DisplaySourceMap`）不需要为表格新增任何逻辑，直接复用图片那套规则。

### 2. 附件里放什么 view：优先自绘，不用 `UICollectionView`

表格这个场景和"长列表"不一样——它是**固定的小规模网格**（几行几列，一次性全部可见），用 `UICollectionView` 反而过重（滚动、cell 复用、layout 计算的开销对一个 5×3 的表格毫无必要），更合适的做法是**自绘一个轻量的 `MarkdownTableView: UIView`**，用简单的网格布局：

```swift
final class MarkdownTableView: UIView {
    private let data: MarkdownTableData
    private let theme: MarkdownTheme
    private var columnWidths: [CGFloat] = []   // 按内容自适应列宽，一次性计算

    override func layoutSubviews() {
        super.layoutSubviews()
        // 按 bounds.width 等比缩放各列宽度（列宽比例在 init 时预计算好）
        layoutCells(columnWidths: scaledColumnWidths(for: bounds.width))
    }

    // 表头加粗背景色、单元格按 columnAlignments 左中右对齐、行间用 theme.colors.tableBorder 画分隔线
}
```

**为什么不用 `UICollectionView`**：
- 表格内容一旦确定就不再变化（除非用户编辑源码），不需要动态增删 cell 的复用机制。
- 列宽需要"整表统一计算"（每列宽度取决于该列所有单元格里最长的内容），这本身就不是 `UICollectionViewFlowLayout` 擅长的场景，用自定义 layout 逻辑直接算更直接。
- 减少一层 `UICollectionViewCell` 复用池、`UICollectionViewDataSource` 的样板代码，对小规模网格是不必要的复杂度。

### 3. `attachmentBounds` 的关键点：宽度撑满容器，高度按内容自适应

```swift
final class MarkdownTableAttachmentViewProvider: NSTextAttachmentViewProvider {
    override func attachmentBounds(for attributes: [NSAttributedString.Key: Any],
                                     location: NSTextLocation,
                                     textContainer: NSTextContainer?,
                                     proposedLineFragment: CGRect,
                                     position: CGPoint) -> CGRect {
        let width = proposedLineFragment.width   // 表格宽度 = 容器可用宽度（与代码块背景同理，撑满而非按内容收缩）
        let tableView = view as! MarkdownTableView
        let height = tableView.intrinsicHeight(forWidth: width)  // 按列宽换算后逐行累加行高
        return CGRect(x: 0, y: 0, width: width, height: height)
    }
}
```

宽表格（列很多、内容很长）的处理：**表格内部允许横向滚动**，而不是压缩字体或换行挤压——把 `MarkdownTableView` 包一层 `UIScrollView`（横向），这样宽表格在窄屏 iPhone 上依然可读，这是移动端表格渲染的标准做法（GitHub App、飞书文档等都是这个思路）。

### 4. 和现有架构的复用关系一览

| 需要的能力                 | 复用哪部分已有设计                                           |
| -------------------------- | ------------------------------------------------------------ |
| 附件承载可交互 view        | 与图片、复制按钮同一套 `NSTextAttachmentViewProvider` 机制（架构文档第 8 节） |
| 源码文字保留+弱化          | 与图片语法处理方式完全一致（`visitImage` 的镜像）            |
| 复制时跳过附件、只复制源码 | 直接复用 `markdownSynthetic` 标记和 `DisplaySourceMap`，零新增逻辑（第 9 节） |
| 增量渲染                   | 表格是一个顶层 `MarkdownBlock`（`BlockKind.table`），编辑表格内容只重渲染这一个块，与其他块级类型待遇相同（第 11 节） |
| Theme 统一管理样式         | 在 `MarkdownTheme` 里新增一个 `Table` 子结构体（表头背景色、边框色、单元格内边距、最小列宽等），不单独造一套配置体系 |

### 一个需要留意的边界情况

swift-markdown 的表格解析依赖 GFM 扩展（`Table` 类型是通过 cmark-gfm 的表格扩展支持的，不是 CommonMark 核心语法），要确认你解析时用的是启用了 GFM 扩展的 parsing options（`Document(parsing:options:)` 里包含 `.parseBlockDirectives` 之外，表格本身在 swift-markdown 里默认是随 cmark-gfm 内置开启的，不需要额外 flag，但建议在正式开发前用一个真实的 GFM 表格 fixture 跑一遍确认 `document.children` 里确实产出了 `Table` 节点，而不是被当成普通段落文本解析掉——这类底层库的实际行为最好实测验证，而不是完全依赖文档描述）。
