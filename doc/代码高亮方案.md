# 代码高亮方案（MarkdownEditorHy4）

> 写给**没写过编辑器、也没写过词法分析**的人。
> 目标：读完之后你能回答三个问题 —— 一次高亮是怎么跑完的、每门语言的差别写在哪、想加一门语言或换个高亮库该动哪几个文件。
> 术语第一次出现都会跟一句大白话解释。想知道「为什么最后变成这样」，见 `doc/bugHistory.md` 第 16 条。

---

## 一、先看全局：一次高亮到底发生了什么

代码块从 markdown 源码变成屏幕上有颜色的代码，中间只有两大步，中间夹着一个「不上色」的代表：

````
markdown 源码
   ```swift
   let x = 1   // 注释
   ```
        │
        │  ① 渲染（MarkupToAttributedRenderer.visitCodeBlock）
        │     把源码变成富文本；此时代码是**纯黑的**，一个字都没上色
        ▼
   富文本（NSAttributedString）
        │
        │  ② 扫描（SimpleCodeHighlighter.highlight）
        │     逐字符看一遍，输出一串「哪几个字是什么角色」
        │     注意：它**只说角色，不说颜色** —— 输出长这样：
        │       [ 0..3 是 keyword, 12..18 是 comment ]
        ▼
   一串 token（HighlightToken）
        │
        │  ③ 上色（MarkupToAttributedRenderer.applySyntaxHighlighting）
        │     拿每个 token 的角色去主题里查颜色，再写回富文本
        │     查表那一步是 MarkdownTheme.color(for:)
        ▼
   屏幕上有颜色的代码
````

**关键设计：②和③是分开的。**

打个比方：高亮器像一个**只贴标签不涂色**的校对员。他拿荧光笔在稿子上贴「这是关键字」「这是注释」的小纸条，但绝不决定用什么颜色。真正决定颜色的是最后一步拿着的**配色表**。

这么做换来两个好处：

- 换配色表（改主题）不用碰扫描器；
- 换扫描器（比如以后换成 tree-sitter 这种更精确的解析器）不用碰配色 —— 颜色风格一模一样，只是「哪些字算关键字」判得更准。

如果让扫描器直接决定颜色，上面这两件事就绑死了：换一个库，整套配色跟着变。

## 二、文件分工：一共 6 个文件

代码都在 `MarkdownEditor/Rendering/Highlighting/` 下（除了渲染器和主题）。

| 文件 | 它负责什么 | 用一句话说 |
|---|---|---|
| `SyntaxRole.swift` | **贴什么标签** | 定义 7 种角色（关键字/字符串/注释/数字/类型/普通标识符/没归类）+ 一个 token 长什么样 |
| `CodeHighlighting.swift` | **要什么** | 一个只有两个方法的协议 `CodeHighlighting`，渲染器只认它，不认任何具体实现 |
| `SimpleCodeHighlighter.swift` | **怎么算** | 真干活的单遍扫描器，性能都在这儿 |
| `CodeLanguageProfile.swift` | **每门语言的差别** | 规则表的数据结构 + 语言名到表的映射 `profile(forLanguage:)`，顺带放着 JavaScript / TypeScript / Python / Swift 四张表 |
| `CodeLanguageProfile+CLike.swift`<br>`+Modern.swift`<br>`+Scripts.swift` | **其余 14 门语言的表** | 纯数据，按语系分三个文件方便对照 |
| `MarkdownTheme.swift`（`CodeSyntaxColors` / `color(for:)`） | **什么颜色** | 角色 → 颜色的唯一映射处 |

外面还有两个「沾边但不管高亮」的：

- `Rendering/CodeBlockInfo.swift`：代码块的**身份标记**。挂在字符上告诉 UI 层「这段是代码块，背景画这儿、复制按钮放这儿、复制的内容是这些」。它跟颜色没关系。
- `Rendering/RenderedFragment.swift`：渲染中间产物。高亮最后就是往它的富文本上写一遍颜色。

> 「协议」是什么：可以理解成一份**接口说明书**。`CodeHighlighting` 这份说明书上写着「你必须能回答支不支持某语言、能给我一串 token」，但完全不关心你是怎么算出来的。渲染器只按照说明书调用，所以谁来当这个高亮器都行。

## 三、主流程：`visitCodeBlock` 里那 7 步

代码位置：`MarkupToAttributedRenderer.visitCodeBlock(_:)`（约第 448 行）。

渲染器是「一个 markdown 语法节点调用一个 `visitXxx` 方法」。碰到代码块就走这个方法，返回一小段富文本（`RenderedFragment`）。

| 步骤 | 干了什么 | 关键方法 / 值 |
|---|---|---|
| 1 | 算出**代码正文**在块源码里的起点 | 先跳过第一行那个由三个反引号组成的围栏行，再 `source.nsRange(of: code, fromUTF16Offset:)`，结果存进 `codeSourceStart` |
| 2 | 把代码正文塞进富文本 | `out.append(.sourceSliced(code, sourceStart:attributes:))` —— **显示的就是源码本身**，不是另写一份 |
| 3 | 把 AST 没覆盖到的字符补进来 | `out.reconciled(withSource:in:orphanAttributes:)` —— 首尾那两行围栏就是这一步补的，顺便给它们弱化色 |
| 4 | 统一段落样式 | `out.addAttributesIfAbsent([.paragraphStyle: codeStyle])` |
| 5 | 打「这是个代码块」的标记 | `out.setAttributes([.markdownCodeBlock: CodeBlockInfo(...)])` —— 给 UI 层画背景、放复制按钮用 |
| 6 | **上色** | `applySyntaxHighlighting(to:code:language:codeSourceStart:)` |
| 7 | 返回 | 交给上层拼成整篇文档 |

第 2 步那句「显示的就是源码本身」是这个项目的地基：屏幕上你看到的每个字符都能在源码里找到对应位置，所以「全选 → 复制」出来的东西**和源文件一模一样**。上色只改颜色、不动文字，因此高亮这套东西对这条不变式零影响，不需要额外补什么逻辑。

### 3.1 上色为什么必须排在最后（本项目最值钱的一条）

`applySyntaxHighlighting` 本身只做一件事：给某些字符写一个 `.foregroundColor`（前景色）属性。这么简单的一步，位置放错能让整个代码块的渲染慢上两个数量级。

原因在一个叫 **attribute run** 的概念上。

> **attribute run（属性小段）是什么**：富文本不是「一个字符串 + 一份属性」，而是被系统按「属性是否一致」切成了很多小段。比如一段文字里前 3 个字是紫色的、后面 10 个字是黑色的，系统内部就记成两段（两个 run），而不是记 13 个字。
> 找它的一种办法：`NSAttributedString` 里那些「遍历所有属性再逐段重设」的操作，代价直接跟**段数**挂钩。

上色会把代码切成上千个小段（每遇到一个关键字、一个字符串就断一次）。而第 3、4 步里用的 `addAttributesIfAbsent`，内部正是「遍历所有段 + 逐段重设属性」这种写法，耗时跟段数强相关。

实测（380 行 Swift 代码，见 `MarkdownEditorHy4Tests/pptmp/HighlightPerfProbe.swift`）：

| 场景 | 耗时 |
|---|---|
| 全量重设属性，文本只有 **1** 个小段 | 0.005 ms |
| 全量重设属性，文本被上色切成 **1140** 个小段 | 6.4 ms |

差了约 **1280 倍**。

所以顺序反了（先上色、再补漏/补样式）的后果是：后面那几步全部在「碎渣」上跑，白花两个数量级的时间。把上色挪到最后则完全免费 —— 它只写一个前景色属性，不会再被谁覆盖。

改前改后的实测（只统计「上色多花的耗时」，即开高亮与关高亮的差）：

| 代码规模 | 改前 | 改后 |
|---|---|---|
| 50 行 | 1.9 ms | 1.3 ms |
| 200 行 | 12.7 ms | 5.0 ms |
| 380 行 | 17.4 ms | 6.8 ms |

对应到端到端（「在代码块里敲一个字」要重渲染这块）：380 行从 103.4 ms 降到 92 ms。

**给后来改这块代码的人的一句话**：`visitCodeBlock` 里那几行调用是**有意排序**的，别按「看起来顺眼」重排。凡是「全量属性操作」（`reconciled` / `addAttributesIfAbsent` / `setAttributes`）统统排在 `applySyntaxHighlighting` 前面。

### 3.2 上色时那个「偏移平移」是干嘛的

扫描器输出的 token，坐标是**从代码正文第一个字算起**的。比如 `let` 是「第 0 到第 3 个字符」。

但到了上色那一步，富文本已经**不是从代码正文开始了** —— 第 3 步的补漏往前面插了第一行 ```` ```swift ````。如果直接把「第 0 个字符」当成「富文本的第 0 个字符」，颜色就会整块往前错一行。

解决办法是反查一下代码正文现在落在哪儿：

- `codeTextStart(in:codeSourceStart:)`：拿步骤 1 记下的 `codeSourceStart`，去 `fragment.mappings` 里找「源码起点正好等于这个值」的那条记录，它的下标就是代码正文在富文本里的起点；
- 找到后，每个 token 的范围统一加上这个位移（代码里叫 `shift`）再写颜色。

> 打个比方：token 说的是「从我家门口往右走 3 步」，但你家门口和它家门口隔了一条街。`codeSourceStart` 就是你俩门口的地址差。

另外上色前还有一道夹紧（`NSIntersectionRange`）：万一扫描器算错了范围越了界，也只是少上一块色，不会让 `addAttribute` 崩掉整篇渲染。

## 四、扫描器：`SimpleCodeHighlighter` 怎么工作

`highlight(_:language:)` 一行代码就能读完：

```
① 查语言表：CodeLanguageProfile.profile(forLanguage:) 拿不到 → 直接返回空（按纯文本显示）
② 代码太长（超过 maximumLength，默认 20000 字符）→ 直接返回空
③ 拆成字符数组 + 建 UTF-16 偏移表 → 交给内部的 Lexer 扫
```

### 4.1 为什么手写扫描而不用正则

用 `NSRegularExpression` 的话，每认一种 token 都要把整段代码从头到尾匹配一遍。一门语言十几条规则，等于把代码扫十几遍；而且每条规则的匹配结果都要做一次坐标换算，来回很贵。

这里的做法是**一趟走完**：每个字符只看一眼，看一眼走一格。代价是精度（下面第七节会说哪些地方故意不精确），但这个编辑器里的高亮本来就是**给眼睛看的** —— 判错了顶多颜色不对，不影响编辑和复制。

### 4.2 扫的顺序（顺序本身很重要）

`Lexer.run()` 里的 8 个分支，从上到下依次判断，命中就跳过去：

| 顺序 | 认什么 | 为什么要排在这儿 |
|---|---|---|
| 1 | 空白（空格/制表/换行） | 最常见，先最快地跳过，不上色 |
| 2 | 注释（`//` / `#` / `--` / `/* */`） | **必须排在预处理指令前面**：PHP / Shell 的 `#` 是行注释，得先被这里领走，不能让下面「`#` 是预处理指令」抢过去 |
| 3 | 预处理指令（`#include` / `#region`） | 且必须**在行首**才算 —— 别处的 `#` 另有含义（SQL Server 的临时表 `#temp`） |
| 4 | 字符串（`"…"` / `'…'` / `` `…` `` / `"""…"""`） | 字符串里的关键字不该被单独上色，所以要在认标识符之前整段吃掉 |
| 5 | `@` 开头的词（`@interface` / `@Override` / `@"…"`） | 只有开了 `supportsAtPrefix` 的语言走这儿 |
| 6 | 数字（含 `0x1F` / `1.5e-8` / `3j`） | 排在标识符前面；标识符不会以数字开头，两者不冲突 |
| 7 | 标识符 / 关键字 | 只有「需要上色」的才产出 token，普通变量名返回 nil |
| 8 | 其余（运算符、括号…） | 不上色，往前走一格 |

### 4.3 两张辅助表（性能上的两个小机关）

扫描前会准备两样东西：

- `scalars: [Unicode.Scalar]`：把代码拆成字符数组。数组按下标取值是 O(1)，比在 String 上用 `index(_:offsetBy:)` 一格一格爬快得多。
- `offsets: [Int]`：**字符下标 → UTF-16 偏移**的对照表。

第二样需要解释一下。上色最终要调 `NSMutableAttributedString.addAttribute(_:value:range:)`，它要的是 **NSRange（UTF-16 坐标）**。而「第 20 个字符」和「UTF-16 里的第 20 号」并不总是同一个数：

> 在 UTF-16 这套记账方式里，常见的字符（英文字母、汉字）都占 1 格，但少数生僻字符和 emoji 要占 2 格。所以「第几个字」不能简单乘个常数换算过去。

一次性把每个位置的偏移算好，后面取任意区间都是查表，扫描时不用小心翼翼地累加。代价是多一次遍历 + 一个跟代码等长的 Int 数组（扫完就释放）。

**具体怎么记的**：`offsets[i]` 就是第 `i` 个字符的 UTF-16 起始位置，最后多放一个「哨兵」表示结尾，这样收尾字符的结束偏移也能直接取到。

### 4.4 只产出「需要上色」的 token

普通变量名、运算符、括号这些一律不产 token。理由很直接：每个 token 都会变成一次 `addAttribute` 调用，少了这些，后面的属性赋值次数能压到最少。

所以 `identifierEnd` 的返回值里，普通标识符的 `role` 是 `nil` —— 意思是「这段我看过了，但它不用上色」。

### 4.5 长度上限：`maximumLength`

默认 20000 字符，超过就整段放弃高亮。

> 这不是精度问题，是保命设置。高亮是**每次重渲染都要重跑**的：在一个代码块里敲一个字，整块都要重新扫一遍。万一有人贴进来一段几万行的日志或机器生成的代码，每次按键都得全扫一遍，输入就开始发顿了。到那个量级也没人在乎颜色，不如直接按纯文本显示。

## 五、每门语言的差别：`CodeLanguageProfile`

### 5.1 表驱动，不是「一门语言一个函数」

扫描逻辑（`SimpleCodeHighlighter`）**只有一份**，各语言的差别全部落在数据上。加一门语言 = 加一个 `static let`，扫描器一行都不用碰。

> 打个比方：扫描器是一台「按说明书办事」的机器，`CodeLanguageProfile` 就是那本说明书。C 的说明书写「行注释是 `//`、认 `#` 开头的预处理指令」，SQL 的说明书写「行注释是 `--`、大小写不敏感」。

### 5.2 字段一览

字段的默认值取的都是「大多数语言都这样」的那个值，所以每张表只写**和默认值不一样**的那几项，一眼扫过去就知道这门语言特别在哪。

| 字段 | 作用 | 谁跟默认值不一样 |
|---|---|---|
| `lineComments` | 行注释的开头，可以好几种 | C 系 `["//"]`；Python `["#"]`；SQL `["--"]`；PHP `["//", "#"]`；JSON 空数组 |
| `supportsBlockComment` | 认不认 `/* … */` | JSON 关掉。**刻意不处理嵌套**（嵌套块注释极少见，收尾早一点只是变色，不影响编辑） |
| `preprocessorPrefix` | 预处理指令引导符 | C / C++ / ObjC / C# 是 `#`；其他语言不配 |
| `supportsAtPrefix` | 认不认 `@` 开头的词 | ObjC / Java / Swift / C# 打开 |
| `stringPrefixes` | 字符串前缀允许的字母 | Python `rbfu`、C# `$`、Rust `rb` |
| `supportsSingleQuotedString` | 认不认 `'…'` | **只有 Rust 关掉** —— Rust 里 `'` 更多是生命周期标记 `&'a str`，当字符串扫会把后面半行都染红 |
| `supportsTripleQuotes` | 认不认 `"""…"""` | Python / Swift / Kotlin / Java / C# |
| `supportsBacktickString` | 认不认 `` `…` ``（且**可跨行**） | JavaScript 模板串、Go 原始串 |
| `radixPrefixes` | `0x` / `0b` / `0o` 这些前缀的第二位允许什么 | C 系 `xXbB`；Shell 只有 `xX`（不认 `0b` / `0o`）；JSON 不配（它的数字没有进制前缀） |
| `treatsCapitalizedAsType` | 大写开头的标识符当类型名 | **SQL / JSON 关掉**（SQL 里 `USER_ID` 这种大写列名一大片，全上色反而看不清关键字；Go 也关，它的大写表示「导出」不是类型） |
| `isCaseInsensitive` | 关键字不分大小写匹配 | **只有 SQL 打开** |
| `keywords` | 关键字 | 每门一张 |
| `typeKeywords` | 该用「类型色」而不是关键字色的词 | `int` / `void` / `boolean`… |
| `literals` | 字面量常量，按数字色上 | `true` / `false` / `nil` / `None` / `NULL` |

⚠️ 两张表之间**不能有重复项**（`void` 只写在类型表里，别在关键字表里再写一遍）—— 测试里有一条专门体检这个，见 `testEveryProfileIsWellFormed`。

### 5.3 支持的 18 门语言

语言名到表的映射在 `CodeLanguageProfile.profile(forLanguage:)`：

| 语系 | 语言 |
|---|---|
| 脚本 / 动态 | JavaScript、TypeScript、Python、Ruby、PHP、Shell |
| C 系 | C、C++、Objective-C、Java、C#、Kotlin、Go、Rust、Swift |
| 查询 / 数据 | SQL、JSON、JSONC |

**别名收了特别多**，这是刻意的：同一个语言，围栏里写什么的都有 —— `cpp` / `c++` / `cxx` / `cc` / `hpp` 都是 C++，`objc` 和 `objective-c` 是同一门，`sh` / `bash` / `zsh` / `console` / `terminal` 都算 Shell。用户不该为了「颜色对上」去猜该写哪个词。大小写也随便（先 `lowercased()` 再查表）。

⚠️ **HTML / CSS / YAML 是刻意没做的**。它们的结构和「按字符一趟扫过去」的做法不搭（HTML 要认标签和属性、YAML 靠缩进定层级），硬套只会得到满屏乱色，不如老实按纯文本显示。

### 5.4 加一门语言要改哪儿

以加一门 `lua` 为例：

1. 在 `CodeLanguageProfile+Scripts.swift` 里加一个 `static let lua = CodeLanguageProfile(...)`，只写和默认值不同的字段（`--` 行注释、`keywords:` 里列 lua 的关键字…）；
2. 在 `profile(forLanguage:)` 的 `switch` 里加一行：`case "lua": return .lua`；
3. 到 `MarkdownEditorHy4Tests/CodeHighlightingMoreLanguagesTests.swift` 里补一条测试（抄隔壁那条改语言名和几行样例代码就行）。

不用改扫描器，也不用改渲染器。

## 六、角色 → 颜色

### 6.1 七种角色

`SyntaxRole` 枚举（`SyntaxRole.swift`）：

| 角色 | 认哪些东西 | 默认颜色 |
|---|---|---|
| `keyword` | `func` / `def` / `const` / `SELECT`… | 紫 |
| `string` | `"abc"` / `'abc'` / `` `abc` `` / `"""…"""` | 红 |
| `comment` | `// …` / `# …` / `-- …` / `/* … */` | 灰绿 |
| `number` | 数字，外加 `true` / `false` / `nil` / `None` 这类字面量常量 | 蓝 |
| `type` | ① 规则表里列出的 `int` / `void`；② **启发式**：大写字母开头的标识符（`NSString` / `List`） | 青 |
| `identifier` | 普通标识符 | 用正文色（**扫描器根本不产这个 token**） |
| `plain` | 空白、运算符等 | 用正文色 |

`type` 那条启发式很省事：各语言的类名 / 结构体名基本都大写开头，命中率够高，省得逐门语言抄一遍内置类型表。

颜色本身只有一个地方定义：`MarkdownTheme.CodeSyntaxColors`（keyword 紫 / string 红 / comment 灰绿 / number 蓝 / type 青）。查表方法是 `MarkdownTheme.color(for:)`。

⚠️ `identifier` 和 `plain` 走的是正文色 `textColor`，**没有单独的「高亮用黑色」** —— 这样换主题它们自动跟着正文走，不用配第二份颜色。

### 6.2 开关

- `MarkdownTheme.enablesCodeHighlighting`（默认 `true`）：关掉之后整块用代码块默认色，和没做高亮时一模一样；
- `MarkupToAttributedRenderer.codeHighlighter`：给 `nil` 就不做高亮。

⚠️ `enablesCodeHighlighting` 是**渲染期读的开关**，颜色是烙进 `NSAttributedString` 里的，所以改完要**整篇重新渲染**才生效（不像背景矩形那样每帧读主题）。

## 七、精度取舍：这是给眼睛看的，不是给编译器看的

不好判、或者判错也无所谓的地方，一律取最省事的写法。翻代码时看到这些别以为是 bug：

| 场景 | 我们的做法 | 后果 |
|---|---|---|
| 嵌套块注释 `/* 外层 /* 内层 */ */` | 遇到第一个 `*/` 就收尾 | 后半段没了注释色，不影响编辑 |
| 模板字符串插值 `` `hello ${user}` `` | 整段算字符串，`${}` 不单独上色 | 插值部分不着色 |
| 非法的进制字面量 `0b12` | 后面一律按十六进制字符集放行 | 整段被吃掉 —— 反正本来就编译不过 |
| 单行字符串遇到换行 | 直接收尾 | 少见的跨行单引号串会断色，但避免把整篇染成一块 |
| 没收尾的字符串 / 块注释 | 剩下全部当字符串 / 注释 | 总好过把后面的代码染成别的颜色 |
| 字符串前缀 + 字符串 | `f"…"` / `$"…"` 连前缀一起算字符串 | 前缀不会被拆出去（拆了颜色会断） |
| `#` 到底是不是预处理指令 | 只在**行首**算 | 行中的 `#temp` 不会被误判 |
| PHP 的 `$variable` | 不上色（`$` 只是变量名的开头，而普通标识符不产 token） | 关键字/字符串/注释/数字照样有色，整体已经够看 |
| Ruby 的 `=begin` / `=end` 块注释 | 没做 | 行注释 `#` 覆盖了 99% 的场景 |
| Shell 的 `#!/bin/bash` | 走行注释那条路，整行按注释色 | 正好符合直觉 |

## 八、性能账（实测数字，别凭感觉优化）

### 8.1 一次「在代码块里敲一个字」的成本

编辑是**只重渲染受影响的块**的 —— `MarkdownDocumentStore.applyEdit(inRenderedRange:replacementText:containerWidth:)`（`MarkdownEditor/Model/MarkdownDocumentStore.swift`）会先算出 `affectedBlockIndices`，只把那一小段重新 parse + 渲染，整篇文档不动。所以敲一个字的模型层成本 ≈ **重渲染一个块**：

| 代码规模 | 耗时（Catalyst + Debug） |
|---|---|
| 2500 字符 | 14 ms |
| 10000 字符 | 48 ms |
| 19000 字符 | 86 ms |

**线性增长**（约 4.4 ms/千字符，没有 O(n²)）。Release 真机上小几倍，比例不变。

### 8.2 高亮在其中只占一小块

想提速，先量「关掉高亮的 `render(blockSource:)` 耗时」—— **渲染管线本身才是大头，高亮只占约 15%**。别一上来就优化扫描器。

### 8.3 量数据的工具

`MarkdownEditorHy4Tests/pptmp/HighlightPerfProbe.swift`（临时探针目录，只看日志不进断言）：

- 跑的是一堆 `measure("标签") { … }`，会往控制台打 `PROBE 标签 = x.xxx ms`；
- 它回答四件事：① 端到端多久 ② 扫描 vs 上色各占多少 ③ 上色把文字切成上千个 run 之后有哪些连带代价 ④ 建偏移表的成本。

测试写法上有两个小工具值得知道（在 `CodeHighlightingTests.swift` 里）：

- `render(code, language:)`：拼一个 ```` ```lang ```` 代码块源码，走一遍真实渲染，返回富文本；
- `colorString(of:in:)`：取某段文字的前景色，转成 `"r,g,b,a"` 字符串再比较。

## 十、想动这块代码时的检查清单

1. **改 `visitCodeBlock` 的调用顺序** → 先想清楚 `applySyntaxHighlighting` 是否还在最后。它不是「顺手写的」，见 3.1。
2. **加语言** → 只动三处：加表、加 `profile(forLanguage:)` 一行、加测试。别去改扫描器。
3. **改扫描器** → 先看 `testcase/代码高亮测试用例.md` 里那 18 段样例跑不跑得过；再跑一遍性能探针确认没变慢（扫描是每键都跑的热路径）。
4. **改颜色 / 加角色** → 颜色只在 `CodeSyntaxColors` 加，`color(for:)` 的 `switch` **要穷举**，别写 `default:`（漏了让编译器拦住）。
5. **想换高亮实现**（tree-sitter 等）→ 实现 `CodeHighlighting` 协议塞给 `renderer.codeHighlighter` 就行，扫描器、渲染器、UI 层都不用改。
