目录组件不应该知道任何关于 `NSAttributedString`、`NSTextAttachment`、TextKit 的事情，编辑器也不应该知道任何关于目录 UI 长什么样的事情。下面给出详细方案。

**在编辑器和目录组件之间插入一个独立的 `OutlineCoordinator`（不属于任何一方，是第三方协调者），双方只与它通信，互不持有对方的引用。编辑器负责产出"标题列表"和"当前光标所在标题"这两类事件，目录组件负责渲染这些数据和发出"用户点了某一项"的事件，`OutlineCoordinator` 做纯粹的数据转发和坐标转换。** 这样任何一方都可以独立替换（比如把目录从侧边栏悬浮面板换成底部弹出的 Action Sheet 列表），另一方完全不需要改代码。

## 1. 整体结构

```
┌─────────────────────┐        ┌───────────────────────┐        ┌─────────────────────┐
│  MarkdownTextView    │        │   OutlineCoordinator    │        │  MarkdownOutlineView  │
│  (已有编辑器)          │        │  (新增，纯数据/事件层)    │        │  (新增，纯 UI 层)       │
│                      │◄──────►│                        │◄──────►│                      │
│  不知道 Outline 长什么样│        │  不知道 TextKit          │        │  不知道 Markdown/TextKit│
│                      │        │  不知道 UI 细节           │        │                      │
└─────────────────────┘        └───────────────────────┘        └─────────────────────┘
```

**依赖方向是关键约束**：编辑器和目录组件都**只依赖 `OutlineCoordinator` 暴露的协议**，彼此之间零引用、零 import。这样将来做"第二个目录 UI 变体"（比如 iPad 上用侧边栏、iPhone 上用底部抽屉）只需要新写一个实现 `MarkdownOutlineDisplaying` 协议的 view，编辑器代码一行不用改。

## 2. `OutlineCoordinator`：协议先行

```swift
/// 大纲里的一个条目——注意这里完全不含任何 TextKit/NSRange/UIFont 的东西，
/// 只有目录 UI 渲染需要的最小信息。
struct OutlineItem: Identifiable, Equatable {
    let id: BlockID          // 复用你架构里已有的 BlockID（第 3.1 节），天然稳定、天然唯一
    let level: Int           // 1...6，对应 H1-H6
    let title: String        // 标题的纯文本内容（去除 markdown 语法符号，比如 "## 标题" 的纯文本部分）
    let sourceOffset: String.Index  // 该标题在 source 中的起始位置，用于点击跳转
}

/// 编辑器需要实现/驱动的一侧：产出数据、接受跳转指令。
protocol MarkdownOutlineDataSource: AnyObject {
    /// 编辑器把当前文档的完整标题列表报告给 Coordinator。
    /// 每次增量渲染影响到任意标题时调用（不需要每次编辑都调用，见第 4 节的节流策略）。
    func currentOutlineItems() -> [OutlineItem]

    /// Coordinator 请求编辑器跳转到指定标题。
    func scrollToOutlineItem(_ item: OutlineItem)
}

/// 目录 UI 需要实现的一侧：接受数据更新、接受高亮指令，上报点击事件。
protocol MarkdownOutlineDisplaying: AnyObject {
    func updateOutlineItems(_ items: [OutlineItem])
    func highlightOutlineItem(_ id: BlockID?)   // nil 表示光标不在任何标题下（文档开头）
}

/// 目录 UI 通过这个协议把用户点击事件报告出去（Coordinator 实现它）。
protocol MarkdownOutlineViewDelegate: AnyObject {
    func outlineView(_ view: MarkdownOutlineDisplaying, didSelect item: OutlineItem)
}
```

`OutlineCoordinator` 本身：

```swift
final class OutlineCoordinator {
    weak var editorDataSource: MarkdownOutlineDataSource?
    weak var outlineView: MarkdownOutlineDisplaying?

    private(set) var items: [OutlineItem] = []
    private var currentHighlightedID: BlockID?

    // MARK: - 编辑器 → Coordinator → 目录 UI

    /// 编辑器在标题结构发生变化时调用（新增/删除/重命名标题、标题层级变化）
    func editorDidUpdateOutline(_ items: [OutlineItem]) {
        self.items = items
        outlineView?.updateOutlineItems(items)
    }

    /// 编辑器在光标位置变化时调用（见第 4 节：需要做节流，不能每次光标移动都触发）
    func editorDidMoveCursor(toBlockID blockID: BlockID?) {
        let ownerHeadingID = findEnclosingHeading(for: blockID)  // 见第 5 节：光标所在块 → 归属标题
        guard ownerHeadingID != currentHighlightedID else { return }
        currentHighlightedID = ownerHeadingID
        outlineView?.highlightOutlineItem(ownerHeadingID)
    }

    // MARK: - 目录 UI → Coordinator → 编辑器

    func outlineDidSelectItem(_ item: OutlineItem) {
        editorDataSource?.scrollToOutlineItem(item)
    }
}

extension OutlineCoordinator: MarkdownOutlineViewDelegate {
    func outlineView(_ view: MarkdownOutlineDisplaying, didSelect item: OutlineItem) {
        outlineDidSelectItem(item)
    }
}
```

**这个类刻意做得很薄**——它不持有 `MarkdownDocumentController`、不 import TextKit、不 import 任何具体的目录 UI 实现类型，全部通过协议交互。它唯一的"业务逻辑"是 `findEnclosingHeading`（第 5 节展开）和高亮变化的去重判断。

## 3. 编辑器侧：如何产出标题列表

在你已有的架构里，`MarkdownDocumentModel` 已经维护着 `blocks: [MarkdownBlock]`，标题只是其中 `kind == .heading(level:)` 的那些块，提取逻辑是现成的：

```swift
extension MarkdownDocumentModel {
    func extractOutlineItems() -> [OutlineItem] {
        blocks.compactMap { block in
            guard case .heading(let level) = block.kind else { return nil }
            let title = plainTextTitle(for: block)  // 从 block.markup 的 Heading 节点取 plainText，
                                                      // 自动去除 # 和行内 ** _ 等语法符号，只留纯文字
            return OutlineItem(id: block.id, level: level, title: title,
                                sourceOffset: block.span.range.lowerBound)
        }
    }
}
```

`Heading` 节点本身有 `.plainText` 属性（swift-markdown 内置，会递归拼接所有 inline 子节点的纯文本、天然去除加粗斜体的语法符号），不需要自己写文本清洗逻辑。

**这一步只在"标题结构可能变化"时触发**，不是每次渲染都重新提取整个列表——挂载点是你已有的增量渲染管线的收尾处（第 11.3 节 `applyIncrementalUpdate` 末尾）：

```swift
// 在 applyIncrementalUpdate 末尾追加
if replacedRange.newBlocks.contains(where: { if case .heading = $0.kind { return true }; return false })
    || replacedRange.oldBlocks.contains(where: { if case .heading = $0.kind { return true }; return false }) {
    outlineCoordinator?.editorDidUpdateOutline(documentModel.extractOutlineItems())
}
```

即"本次增量更新涉及的新块或被替换掉的旧块里，只要有一个是标题"，才重新提取并通知——这个判断本身是 `O(受影响块数)`，不会因为文档很长而变慢，普通正文编辑（不涉及标题）完全不会触发目录更新。

## 4. 跳转：点击目录 → 编辑器定位

```swift
extension MarkdownTextView: MarkdownOutlineDataSource {
    func scrollToOutlineItem(_ item: OutlineItem) {
        // sourceOffset 是 source 坐标系，需要转换到显示坐标系（复用 9.2 节已有的映射机制，反方向使用）
        guard let displayLocation = documentController.displayLocation(forSourceIndex: item.sourceOffset) else { return }

        let range = NSRange(location: displayLocation, length: 0)
        // 移动光标 + 滚动到可见位置
        selectedRange = range
        scrollRangeToVisible(range)

        // 可选：短暂高亮该标题所在行，给用户明确的视觉反馈（类似 Xcode 跳转到定义时的高亮闪烁）
        flashHighlight(at: range)

        becomeFirstResponder()  // 让光标真正落位，用户可以直接开始编辑
    }
}
```

这里复用的是你在复制拦截（第 9.2 节）里已经建好的 `DisplaySourceMap`——它是双向的，"source 坐标 → 显示坐标"这个方向本来就需要支持（增量渲染时要用它反查显示区间），不需要为目录跳转专门新增一套映射逻辑。

## 5. 高亮：光标位置 → 归属标题的判定

这是这个功能里唯一需要一点新逻辑的地方——"用户光标在哪个标题的内容里"本质是一个**区间归属查询**：给定光标所在的 `MarkdownBlock`，找到它前面最近的、层级不低于它的标题。

```swift
extension OutlineCoordinator {
    /// blockID 是光标当前所在的顶层块（可能是段落、列表、代码块，也可能就是标题本身）
    private func findEnclosingHeading(for blockID: BlockID?) -> BlockID? {
        guard let blockID, let index = items.firstIndex(where: { $0.id == blockID }) else {
            // 光标所在块本身不是标题，需要问编辑器"这个 blockID 在文档顺序里排第几"，
            // 然后找 items 数组里 sourceOffset 小于等于它、且离它最近的那个标题
            return findNearestPrecedingHeading(beforeBlockID: blockID)
        }
        return items[index].id  // 光标就在标题这一行本身
    }

    private func findNearestPrecedingHeading(beforeBlockID: BlockID?) -> BlockID? {
        guard let beforeBlockID,
              let cursorOffset = editorDataSource?.sourceOffset(forBlockID: beforeBlockID) else { return nil }
        // items 按文档顺序排列（sourceOffset 递增），二分查找 <= cursorOffset 的最后一个标题
        return items.last(where: { $0.sourceOffset <= cursorOffset })?.id
    }
}
```

需要给 `MarkdownOutlineDataSource` 协议再加一个小方法支持这个查询：

```swift
protocol MarkdownOutlineDataSource: AnyObject {
    func currentOutlineItems() -> [OutlineItem]
    func scrollToOutlineItem(_ item: OutlineItem)
    func sourceOffset(forBlockID: BlockID) -> String.Index?   // 新增
}
```

**注意这里刻意没有实现"多级嵌套高亮"（比如 H2 光标时，目录里对应的 H1 父项也一起高亮）**——按你的需求"高亮那一行"，先做单项高亮即可。如果未来要做层级高亮（面包屑式），只需要在 `findEnclosingHeading` 里从当前标题项往前继续找"层级更小的最近标题"，串成一条链返回 `[BlockID]` 而不是单个 `BlockID?`，`highlightOutlineItem` 协议方法签名改一下即可，不影响其他部分。

## 6. 光标位置事件从编辑器发出：节流是关键

用户拖动光标或快速打字时，`selectionDidChange` 会被高频触发，如果每次都做"查找归属标题 + 通知 UI 刷新"，在长文档上可能有性能顾虑（虽然二分查找本身很快，但频繁的 UI 高亮动画切换体验也不好）。

```swift
extension MarkdownTextView: UITextViewDelegate {
    func textViewDidChangeSelection(_ textView: UITextView) {
        outlineCursorUpdateDebouncer.schedule { [weak self] in
            guard let self else { return }
            let blockID = documentController.blockID(atDisplayLocation: selectedRange.location)
            outlineCoordinator?.editorDidMoveCursor(toBlockID: blockID)
        }
    }
}
```

`outlineCursorUpdateDebouncer` 是一个简单的防抖工具（比如 100-150ms 延迟合并连续触发），因为"目录高亮跟随光标"是一个**辅助感知功能**，不需要逐字符级别的实时性，防抖既降低了计算频率、也让目录高亮的视觉变化不会因为打字过快而闪烁跳动。

## 7. 目录 UI 组件本身：完全不知道 Markdown

```swift
final class MarkdownOutlineView: UIView, MarkdownOutlineDisplaying {
    weak var delegate: MarkdownOutlineViewDelegate?
    private var items: [OutlineItem] = []
    private var highlightedID: BlockID?
    private var rows: [BlockID: OutlineRowView] = [:]

    func updateOutlineItems(_ items: [OutlineItem]) {
        self.items = items
        rebuildRows()   // 按 level 决定每行缩进，level 1 无缩进，level 2 缩进一档，以此类推
    }

    func highlightOutlineItem(_ id: BlockID?) {
        rows[highlightedID ?? id]?.setHighlighted(false)
        highlightedID = id
        if let id { rows[id]?.setHighlighted(true) }
        if let id, let row = rows[id] { scrollRowIntoView(row) }  // 长文档目录本身也可能需要滚动
    }

    private func handleRowTap(_ item: OutlineItem) {
        delegate?.outlineView(self, didSelect: item)
    }
}
```

这个类的 import 列表里**不应该出现 `Markdown`（swift-markdown 库）、不应该出现 `NSTextLayoutManager`、不应该出现任何 `MarkdownTheme` 类型**——它只认识 `OutlineItem` 这个纯数据结构。这是验证"解耦是否做到位"的一个很实用的检查方法：如果某天你发现目录 UI 的代码里需要 import 编辑器相关的模块才能编译，说明耦合已经渗透进来了。

## 8. 装配：谁负责把三者连起来

`OutlineCoordinator` 不应该在编辑器或目录 UI 内部创建——应该由**更上层的容器**（比如 `MarkdownEditorViewController`）持有并装配：

```swift
final class MarkdownEditorViewController: UIViewController {
    private let textView: MarkdownTextView
    private let outlineView: MarkdownOutlineView
    private let outlineCoordinator = OutlineCoordinator()

    override func viewDidLoad() {
        super.viewDidLoad()
        outlineCoordinator.editorDataSource = textView
        outlineCoordinator.outlineView = outlineView
        outlineView.delegate = outlineCoordinator
        textView.outlineCoordinator = outlineCoordinator   // 编辑器只需要知道"通知谁"，不需要知道目录 UI 本身

        // 初次加载文档后主动推一次
        outlineCoordinator.editorDidUpdateOutline(documentModel.extractOutlineItems())
    }
}
```

这样三者的生命周期和组装关系集中在一处，`MarkdownTextView` 和 `MarkdownOutlineView` 各自的初始化都不需要传入对方的实例。

## 9. 模块归属

按你现有的模块划分（第 13 节），建议新增一个独立 target，不挂在 `MarkdownTextKit` 或任何现有模块下：

```
MarkdownOutline/                       # 新增，独立 target
├── OutlineItem.swift                  # 纯数据结构
├── MarkdownOutlineDataSource.swift    # 协议
├── MarkdownOutlineDisplaying.swift    # 协议
├── OutlineCoordinator.swift           # 协调者，不依赖 UIKit 具体 view 实现
└── MarkdownOutlineView.swift          # 默认 UI 实现（悬浮面板），可以被替换/新增变体
```

`OutlineCoordinator.swift` 和 `OutlineItem.swift` 甚至可以不依赖 UIKit（纯 `Foundation`），只有具体的 `MarkdownOutlineView` 才依赖 UIKit 做视觉呈现——这样万一未来要在 SwiftUI 或者 Mac 原生 AppKit 界面里复用同一套大纲逻辑，协调层完全不用动，只需要新写一个实现 `MarkdownOutlineDisplaying` 的 SwiftUI View。

## 需求对照表

| 需求 | 对应设计 |
|---|---|
| 独立的悬浮目录 UI 组件 | `MarkdownOutlineView`，UIKit view，可挂在任意容器上（悬浮面板/侧边栏均可） |
| 包含所有 H1-H6 | `extractOutlineItems()` 遍历 `blocks` 中 `.heading` 类型，`level` 字段区分层级 |
| 点击标题定位到源码位置 | `OutlineItem.sourceOffset` + `scrollToOutlineItem`，复用已有的 source↔display 坐标映射 |
| 光标所在标题高亮 | `editorDidMoveCursor` + `findEnclosingHeading` 区间归属查询，防抖处理高频光标事件 |
| 不耦合，只传递事件 | `OutlineCoordinator` 作为第三方协调者，双方仅依赖协议，`MarkdownOutlineView` 不 import 任何编辑器/markdown 相关类型 |
