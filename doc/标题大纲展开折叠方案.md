折叠是这个问题里真正的难点，先说明为什么——你现在要处理的不再是一个"扁平列表"，而是一棵**树**（H1 下面挂 H2，H2 下面挂 H3...），折叠意味着"隐藏某个节点的所有后代"，而且折叠状态还要在数据更新（用户在编辑器里改标题）时被**保留**（用户折叠了 H1，编辑器里改了一下 H3 的文字，H1 不应该自动展开）。这几件事放在一起，用 `UIStackView` 手动摆几十个 `UIView` 是撑不住的，需要上专门为"大量同构行、按需显示"设计的组件。

## 结论先行

**用 `UICollectionView` + `UICollectionViewDiffableDataSource` + `NSDiffableDataSourceSectionSnapshot`（这是系统专门为"树状可展开列表"设计的 API，`Files.app`、系统设置的分组列表都是这个底层），折叠状态维护在 `MarkdownOutlineView` 内部自己的树结构里，不依赖 collection view 的 snapshot 作为唯一数据源。** 这样能同时拿到系统级的 cell 复用（长文档几百个标题也不会卡）、原生的展开/折叠动画、以及"折叠状态独立于数据更新"的正确性保证。

## 1. 为什么不能用扁平数组 + `UITableView`/`UIStackView`

先排除两个直觉方案，说明原因：

- **`UIStackView` 逐行摆放**：折叠一个 H1，需要手动把它底下所有 H2-H6 的 `UIView` 设 `isHidden = true`（或从 stack 里移除）。看起来简单，但"用户光标移动到某个被折叠的标题下面的正文"这种场景（第 5 节讨论过的 `findEnclosingHeading`）此时应该做什么？高亮一个隐藏的行，用户根本看不到反馈。而且几十上百个标题时，`UIStackView` 本身的 layout 性能在频繁增删 arranged subview 时并不好，不是为"大量条目、按需显示"设计的。
- **`UITableView` + 扁平数组，折叠时手动增删 row**：可行，但你要自己维护"哪些行当前可见"这个数组，每次折叠/展开都要手写 `deleteRows`/`insertRows` 的 index path 计算，逻辑上和 `UICollectionViewDiffableDataSource` 做的事情一样，但要自己重新实现一遍，容易出 index 计算错误的 bug。

**用系统的 `NSDiffableDataSourceSectionSnapshot`**——它天生就是"父子层级 + 每个节点独立的展开/折叠状态"模型，折叠展开是它的核心能力（`expand(_:)`/`collapse(_:)`），不需要自己算 index path，动画也是系统免费提供的。

## 2. 数据结构：把扁平的 `OutlineItem` 数组转成树

上一轮给的 `OutlineItem` 是扁平数组（按文档顺序排列，只有 `level` 字段），这里需要在 `MarkdownOutlineView` 内部（**注意：不是在 Coordinator 里**，树形结构是"目录 UI 自己的呈现细节"，Coordinator 传过来的还是扁平数组，保持上一轮定的"Coordinator 只传纯数据、不掺入 UI 呈现逻辑"的边界）转换：

```swift
/// 目录 UI 内部使用的树节点，包裹上一轮的 OutlineItem。
/// class 而非 struct：需要在 diffable data source 里被引用比较、且折叠状态要能被外部函数原地修改。
final class OutlineNode: Hashable {
    let item: OutlineItem
    weak var parent: OutlineNode?
    var children: [OutlineNode] = []

    static func == (lhs: OutlineNode, rhs: OutlineNode) -> Bool { lhs.item.id == rhs.item.id }
    func hash(into hasher: inout Hasher) { hasher.combine(item.id) }
}

/// 扁平数组 -> 树，一次线性扫描即可，用一个"栈"记录每一层最近的父节点
func buildOutlineTree(from items: [OutlineItem]) -> [OutlineNode] {
    var roots: [OutlineNode] = []
    var stack: [OutlineNode] = []  // stack.last 是当前层级链条上最近的祖先

    for item in items {
        let node = OutlineNode(item: item)
        while let top = stack.last, top.item.level >= item.level {
            stack.removeLast()
        }
        if let parent = stack.last {
            node.parent = parent
            parent.children.append(node)
        } else {
            roots.append(node)
        }
        stack.append(node)
    }
    return roots
}
```

这个转换是 `O(n)`，n 是标题总数（不是文档总字符数），即使几百个标题也是毫秒级，可以每次收到 Coordinator 的 `updateOutlineItems` 调用时直接重建整棵树，不需要增量更新树结构本身——**真正需要增量/高性能处理的是"折叠状态的保留"和"collection view 的 diff 更新"，不是树的构建**。

## 3. 折叠状态：独立维护，与数据更新解耦

这是你问题里最容易被忽略、但决定"打字编辑时目录不会莫名其妙展开/闪烁"的关键点。折叠状态**不应该存在 `OutlineNode` 或 `OutlineItem` 里**（因为这两者会随每次编辑重建），而应该用一个独立的、跨重建保持的集合：

```swift
final class MarkdownOutlineView: UIView, MarkdownOutlineDisplaying {
    /// 跨越多次 updateOutlineItems 调用持续存在。
    /// 存储「折叠节点」的稳定标识（BlockID 天然稳定，见上一轮方案——
    /// 即使标题文字改了、前后插入了新标题，只要这个标题块本身没被删除，BlockID 不变）。
    private var collapsedNodeIDs: Set<BlockID> = []

    func updateOutlineItems(_ items: [OutlineItem]) {
        let roots = buildOutlineTree(from: items)
        applySnapshot(roots: roots, collapsedIDs: collapsedNodeIDs)
    }

    private func toggleCollapse(_ node: OutlineNode) {
        if collapsedNodeIDs.contains(node.item.id) {
            collapsedNodeIDs.remove(node.item.id)
        } else {
            collapsedNodeIDs.insert(node.item.id)
        }
        applySnapshot(roots: currentRoots, collapsedIDs: collapsedNodeIDs)
    }
}
```

**为什么这样设计是对的**：用户编辑文档时，只要某个标题没被删除，它的 `BlockID` 就不变（这是上一轮方案里 `BlockID` 设计为"稳定标识、不依赖数组下标"的直接价值体现——这里第二次复用到了）。所以哪怕整棵 `OutlineNode` 树因为一次编辑被完全重建，`collapsedNodeIDs` 这个 `Set<BlockID>` 依然精确对应到"用户之前折叠的那些标题"，不会因为重建而丢失或错位。

## 4. 用 `NSDiffableDataSourceSectionSnapshot` 应用折叠状态

```swift
extension MarkdownOutlineView {
    private func applySnapshot(roots: [OutlineNode], collapsedIDs: Set<BlockID>) {
        var snapshot = NSDiffableDataSourceSectionSnapshot<OutlineNode>()

        func addRecursively(_ nodes: [OutlineNode], parent: OutlineNode?) {
            snapshot.append(nodes, to: parent)
            for node in nodes where !node.children.isEmpty {
                addRecursively(node.children, parent: node)
                // 只对「原本就有子节点」的项设置展开状态，叶子节点没有 disclosure 箭头
                if collapsedIDs.contains(node.item.id) {
                    snapshot.collapse([node])
                } else {
                    snapshot.expand([node])
                }
            }
        }
        addRecursively(roots, parent: nil)

        currentRoots = roots
        dataSource.apply(snapshot, to: .main, animatingDifferences: true)
    }
}
```

`NSDiffableDataSourceSectionSnapshot` 会自动做 diff——**只有真正发生变化的行才会有插入/删除/移动动画**，没变化的行（哪怕折叠状态导致它们在屏幕上的 y 坐标变了）由 `UICollectionViewCompositionalLayout` 自动重新排布，不需要你手写任何 index path 计算，这是选它而不是手搓 `UITableView` 增删的核心收益。

## 5. Cell 配置：`UICollectionViewCell` + disclosure 按钮

```swift
final class OutlineRowCell: UICollectionViewListCell {
    func configure(with node: OutlineNode, isHighlighted: Bool, theme: OutlineTheme) {
        var content = UIListContentConfiguration.cell()
        content.text = node.item.title
        content.textProperties.font = theme.font(forLevel: node.item.level)
        contentConfiguration = content

        // 系统原生 disclosure indicator：只有有子节点的行才显示箭头，点击自动触发展开/折叠，
        // 不需要自己画箭头图标、不需要自己处理点击区域
        accessories = node.children.isEmpty ? [] : [.outlineDisclosure()]

        backgroundConfiguration = isHighlighted ? .highlightedListCell(theme: theme) : .listCell()
        indentationLevel = node.item.level - 1
    }
}
```

`.outlineDisclosure()` 这个系统内置的 accessory 是关键——它不仅画箭头，**点击它会自动调用 `sectionSnapshotHandlers.shouldExpandItem`/折叠回调**，你只需要在 `UICollectionViewDiffableDataSource` 上挂一个处理器同步回你自己的 `collapsedNodeIDs`：

```swift
dataSource.sectionSnapshotHandlers.willCollapseItem = { [weak self] node, _ in
    self?.collapsedNodeIDs.insert(node.item.id)
}
dataSource.sectionSnapshotHandlers.willExpandItem = { [weak self] node, _ in
    self?.collapsedNodeIDs.remove(node.item.id)
}
```

这样"点箭头折叠"这个动作，系统 UI 交互和你自己维护的 `collapsedNodeIDs` 状态**始终保持同步**，不会出现"点了折叠，但下次数据更新时又展开了"的不一致。

## 6. 高亮跟随光标：折叠场景下的正确行为

回到你这一轮问题的第一部分——"除了高亮选中"，折叠加进来后，`highlightOutlineItem` 需要多处理一种情况：**如果当前应该高亮的标题被折叠隐藏了（它是某个折叠节点的后代），应该转而高亮那个折叠起来的祖先节点**，而不是高亮一个用户看不见的行：

```swift
func highlightOutlineItem(_ id: BlockID?) {
    var targetID = id
    // 沿父链向上找，直到找到一个「自己或某个祖先没有被折叠」的可见节点
    if let node = nodeIndex[id ?? BlockID.invalid] {
        var current: OutlineNode? = node
        while let n = current, let parent = n.parent, collapsedNodeIDs.contains(parent.item.id) {
            current = parent
        }
        targetID = current?.item.id
    }

    rows[previousHighlightedID]?.setHighlighted(false)
    previousHighlightedID = targetID
    if let targetID { rows[targetID]?.setHighlighted(true) }
}
```

这正是折叠功能存在时，"高亮"这个已有需求必须做的**唯一**调整——其余高亮逻辑（防抖、`findEnclosingHeading` 区间归属查询）完全不用动，上一轮方案里 Coordinator 层的代码一行都不需要改，因为折叠是纯粹的 UI 呈现细节，Coordinator 传过来的还是"哪个 BlockID 该高亮"这一件事，至于这个 ID 对应的行现在是否可见、要不要转移到祖先行上显示，是 `MarkdownOutlineView` 自己该操心的事——这就是上一轮强调的解耦边界在这里继续生效的体现。

## 7. 性能特征总结

| 操作 | 复杂度 | 说明 |
|---|---|---|
| 文档编辑触发标题更新 | `O(标题总数)` 重建树 + diffable snapshot 的内部 diff（系统实现，通常是高效的基于 hash 的 diff） | 标题数量级通常是几十到大几百，即使长文档也远小于总字符数，重建树本身不是瓶颈 |
| 折叠/展开单个节点 | `O(该节点可见后代数)`，由系统 collection view 的 diff+动画机制处理 | 不需要手写 index path 计算 |
| 光标移动触发高亮 | `O(log n)` 二分查找归属标题（上一轮已有）+ `O(树深度)` 向上找可见祖先 | 树深度最多 5-6 层（H1-H6），可忽略不计 |
| 长文档大量标题的显示 | `UICollectionView` 原生 cell 复用，只有可见的几十行会真正创建 view | 不会因为文档有几百个标题就常驻几百个 view |


`OutlineNode`、折叠状态集合、`UICollectionView` 相关的一切，都严格留在这个模块内部，**`OutlineCoordinator` 和它对外暴露的协议完全不变**——这也是当初把"目录 UI 内部实现"和"跨组件通信协议"分开设计的价值：加一个"折叠"这么大的功能，编辑器那一侧的代码零改动，改动完全收敛在目录组件自己的实现细节里。
