引用块背景为什么会赖在原地几百毫秒

在引用块上面敲一个回车，文字当场就往下挪了一行，引用那层淡底色却先留在老地方，过几百毫秒才跳下去。竖条跟着一起犯。

代码块那个同类问题（见 `代码块装饰.md`）已经修好了。这次是引用块独有的一条路，跟「问早了」没关系。坐标其实当场就是准的。问题是那一刻屏幕上同时挂着两块底色。

## 量出来的现场

模拟器，420×800 的编辑器。文档是 `AAA` 加一个空行再加两行引用，光标停在 `AAA` 后面按回车。

| 时刻 | 画出来的引用层 |
| --- | --- |
| 按回车之前 | `id=5`，y=84 |
| 按完回车当场 | `id=5`，y=84 ＋ `id=6`，y=118 |
| 0.6 秒之后 | `id=6`，y=118 |

当场那一栏是关键。新位置的底色（118）已经画对了。旧位置那块（84）没被撤掉，两块叠在一起。旧的那块要等 0.3 秒后那次整篇重算才消失。用户看到的就是「先赖一会儿，再啪地跳」。

## 两块底色是哪儿来的

引用层的标识（渲染层打的 `.markdownQuoteChain`）是**该层 BlockQuote 在源码里的起始位置**。在它上方敲一个回车，后面所有块的起始位置都往后挪。重渲染之后，同一个引用块拿到的是**新标识**（实测 5 变成 6）。

「只重算视野附近」这条路径有个兜底动作。它怕视野外的竖条这一轮没算到、从界面上消失，会把「上一轮有、这一轮没有」的层按旧坐标补回来。旧标识正好落进这个口子。它这一轮确实没有（属性已经被新标识替换了），于是被当成「视野外没算到」，照旧坐标补了一份。

代码块不犯这个毛病。它认的是**对象身份**（同一个 `CodeBlockInfo` 才算同一块），压根没有这个补齐动作。

## 改法

把兜底动作的要求收紧。只补**明确因「整段都在视野外」而跳过**的层，不再「上一轮有、这一轮没有就补」。

```swift
var skippedIDs: Set<Int> = []

for (range, chain) in marked {
    if let band, !chain.ids.isEmpty, chain.ids.allSatisfy({ id in
        guard let cached = quoteBarFrames.first(where: { $0.id == id }) else { return false }
        return !cached.frame.intersects(band)
    }) {
        skippedIDs.formUnion(chain.ids)   // 记下来，这是被跳过的，不是被取代的
        continue
    }
    ...
}

for bar in quoteBarFrames where merged[bar.id] == nil && skippedIDs.contains(bar.id) {
    merged[bar.id] = ...
}
```

旧标识压根不在这一轮扫出来的标记里，进不了 `skippedIDs`，残留的那块当场就没了。改动集中在 `MarkdownTextView+Decorations.swift` 的 `computeQuoteBarFrames`。

## 怎么保证它不会再犯

`MarkdownDecorationSettleLagTests` 里加了一条用例。按完回车当场，引用层只能有一条、底色只能铺一块。当场量到的坐标也必须等于 0.6 秒后的真值。

把它守住的那行改回旧写法（`&& skippedIDs.contains(...)` 换成不设限），这条用例立刻红。红出来的三组数正是上面那张表，2 条对 1 条、2 块对 1 块、84 对 118。

## 顺带说明

引用层的标识会随插入位置变化，这件事本身没动。它只影响「上一轮的缓存还能不能对上号」，不影响正确性。位置每次都是按 fragment 现算的。真要让它彻底稳定（改用「第几个引用块」当标识），牵动的面大得多，这次没必要。
