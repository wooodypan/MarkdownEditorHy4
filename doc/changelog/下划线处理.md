按下 ⌘U，屏幕上终于看得出变化了

markdown 自己没有下划线语法，所以这个编辑器按通行的写法，让 ⌘U 往源码里写一对内联 HTML 的 `<u>` 和 `</u>`。以前这两个词只是显示成灰色的语法标记，中间那段文字一点变化都没有。用户按下 ⌘U，屏幕上毫无反应，看着像快捷键坏了。

导出成 HTML 时还有第二桩麻烦。那对标签被算进「源码里手写的 HTML」，一律转义成纯文本，导出来是 `&lt;u&gt;重点&lt;/u&gt;` 这样一串符号。编辑器里看着还行，导出去全是乱码一样的字。

## 下划线只画在标签之间

改法是在渲染层认出这两个标签。碰到 `<u>` 就把一个开关打开，碰到 `</u>` 关掉；中间那段文字取样式时看到开关是开的，顺手加一条下划线。

标签自己走的是「语法标记」那套样式，不经过这一步，所以 `<u>` 和 `</u>` 这两个词仍然是没有下划线的灰字，跟以前长得一样。源码里确实写着这几个字符，藏起来就不叫「所见即所得」了。

一个块开始渲染时开关会归零。源码里只写了一个孤零零的 `<u>`、后面忘了闭，下划线也就只在本块里淌一段，不会一路染到下一个块去。

带属性的写法不认。`<u class="x">` 到底想表达什么，得先解析属性才说得清，而渲染这一层不该顺手干解析的活。

线的样式放在主题里。`underlineStyle` 决定画什么线（默认单线，就是最常见的那条细线），`underlineColor` 决定线的颜色，留空表示跟着文字颜色走，正文是黑色就画黑线，链接是蓝色就画蓝线，这也是系统默认的行为。

## 导出时要不要放行这对标签

要放行，但只放行干干净净的 `<u>` 和 `</u>` 这两个字符串。

判据是「整段文本正好等于这两个串之一」，不是「标签名叫 u 就放行」。带属性的写法（`<u onclick="alert(1)">`）照样被转义成纯文本。这两个串既不带属性也不带事件，没有可下手的地方；而按整串比较这个判据简单到不可能写错，比解析一遍标签再逐个过滤属性稳当得多。

其余一切照旧。`<b>`、`<div>`、`<span style="...">` 这些还是转义成纯文本显示，导出 HTML 那条路上唯一的例外就是这对下划线标签。

## 怎么保证它不会再犯

新加了 `MarkdownUnderlineTests`，九条用例。渲染这边守四件事，标签之间的字有线、标签自己没线、字体颜色没被动过、忘了闭标签不会淌到下一个块。导出这边守三件事，`<u>重点</u>` 原样输出、`<b>` 照旧转义、带属性的 `<u>` 照样转义。
