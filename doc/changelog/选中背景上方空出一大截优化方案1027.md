- **平移量的公式。** `shift = 字形盒中心 − 行盒中心`,只平移、不改高度,多行选区仍然首尾相接。
- **坐标换算。** 两个中心都在 container 坐标里量,相减后 `textContainerInset` 和滚动偏移抵消,再加到 view 坐标的 `box` 上,没有问题。
- **复用 `textGlyphVerticalBounds`。** 它按每个字符的字体度量算,比 `extra/2` 估算更准。
- **子类写法。** `UITextSelectionRect` 的几个只读属性用计算属性覆盖是合法的。

## 要先解决的问题(按严重程度)

1. **系统高亮不一定读 `selectionRects(for:)`。** TextKit 2 的 `UITextView` 内部画选区,不一定走这个公开方法。它很可能只影响选区手柄、编辑菜单这类周边东西。先做个 1 分钟实验:临时让所有矩形 `offsetBy(dx: 0, dy: 20)`,在真机上选几个字。高亮没动的话,整个方案不成立,要改自绘高亮,或者走上一条回答里的 `lineSpacing` 方案。

2. **用整段(fragment)而不是被选中的那一行来算。**
   - 折行段落里只选第二行时,你拿的是整段所有行的字形范围和整段框的中心。字号都一样时结果近似,混了标题、行内代码或脚注上标就会偏。
   - 更稳的做法是只取矩形所在的那一行,并且拿 `box.midY - textContainerInset.top` 当"行盒中心"。这样的含义是"把字形放到系统实际画的那块矩形正中",不用依赖 `layoutFragmentFrame` 是否含段距。
   - 仓库的注释暗示 fragment 框不含段前和段后间距,但我没有实测,上面这种写法能绕开这个假设。

3. **没有限制只改用了行高倍数的段落。**
   - 图片、公式、表格占位(`blockAttachmentParagraphStyle`、`mathBlockParagraphStyle`)是"故意不套行高倍数"的。
   - 现在它们只要字形盒和行盒中线差超过 0.5pt,选区就会被挪动,而这类行本来是对的。
   - 建议在算之前先读该段的 `paragraphStyle`,`lineHeightMultiple <= 1` 就直接返回。

4. **用 `closestPosition(to:)` 反查字符,在段落边界上可能落到下一段。** 再用 `textLayoutFragment(for: location)` 就会拿到相邻段落(比如标题和正文),算出另一种字体的偏移。更直接的做法是用 `textLayoutManager.textLayoutFragment(for: CGPoint)`,传入 `box.midX/midY` 减去 inset 的 container 坐标,再按 y 在 `textLineFragments` 里找到那一行,不经过字符偏移。

5. **性能。**
   - 拖动选区时这个方法每帧都会被调用。在长文档里全选,会对每一行做反查、`textLayoutFragment(for:)`(它会按需触发排版)和属性枚举,可能整篇同步排版而卡顿。
   - 建议在一次调用内按 fragment 缓存结果。
   - 位置还没排好(`fragment.state != .layoutAvailable`)的直接返回原矩形。这类 fragment 的 `textLineFragments` 是空的,`layoutFragmentFrame` 也只是估算值(`FoldAnchorInfo.swift:21` 有说明)。

## 其他注意

- **光标和手柄。** 没覆盖 `caretRect(for:)`,光标仍是整个行盒高度;手柄锚在选区矩形上,会跟着高亮一起下移。选中后看一眼手柄是否和高亮对齐。
- **搜索高亮还是偏的。** `MarkdownTextView+Search.swift:346-353` 的 `segmentFrames` 也用整行矩形,不改的话查找高亮会比选中高亮高一截。建议把"算位移"抽成一个函数,两处共用。
- **注释里"下方恒定留 ~2.4pt"不严谨。** 这个值和字体有关,标题就不是 2.4。算法本身没有依赖它,可以改成"按字体度量实时算"。

## 1. `MarkdownTextView+Decorations.swift`:给 `textGlyphVerticalBounds` 加一个可选参数

只加了 `nearestToY`:传入时只量离这个 y 最近的那一行,不传则和原来完全一样,现有的代码块和引用调用不受影响。

```swift
func textGlyphVerticalBounds(of fragment: NSTextLayoutFragment,
                             fragmentStart: Int,
                             nearestToY y: CGFloat? = nil) -> (top: CGFloat, bottom: CGFloat)? {
    let fragmentTop = fragment.layoutFragmentFrame.minY
    var top = CGFloat.greatestFiniteMagnitude
    var bottom = -CGFloat.greatestFiniteMagnitude

    // 传了 y 就只量离它最近的那一行（容器坐标），否则量整段所有行
    var lines = fragment.textLineFragments
    if let y {
        func distance(_ line: NSTextLineFragment) -> CGFloat {
            let box = line.typographicBounds
            let lineTop = fragmentTop + box.minY
            let lineBottom = fragmentTop + box.maxY
            return y < lineTop ? lineTop - y : (y > lineBottom ? y - lineBottom : 0)
        }
        lines = fragment.textLineFragments.min(by: { distance($0) < distance($1) }).map { [$0] } ?? []
    }

    for line in lines {
        let lineBox = line.typographicBounds
        guard !lineBox.isNull, lineBox.height > 0 else { continue }
        let baseline = fragmentTop + lineBox.minY + line.glyphOrigin.y

        var ascent: CGFloat = 0
        var descent: CGFloat = 0
        var hasMetric = false
        let lineRange = NSRange(location: fragmentStart + line.characterRange.location,
                                length: line.characterRange.length)
        if lineRange.length > 0, NSMaxRange(lineRange) <= textStorage.length {
            textStorage.enumerateAttributes(in: lineRange, options: []) { attributes, _, _ in
                if let font = attributes[.font] as? UIFont {
                    ascent = max(ascent, font.ascender)
                    descent = max(descent, -font.descender)
                    hasMetric = true
                }
                if let attachment = attributes[.attachment] as? NSTextAttachment {
                    ascent = max(ascent, attachment.bounds.maxY)
                    descent = max(descent, -attachment.bounds.minY)
                    hasMetric = true
                }
            }
        }

        if hasMetric {
            top = min(top, baseline - ascent)
            bottom = max(bottom, baseline + descent)
        } else {
            top = min(top, fragmentTop + lineBox.minY)
            bottom = max(bottom, fragmentTop + lineBox.maxY)
        }
    }

    return top <= bottom ? (top, bottom) : nil
}
```

## 2. `MarkdownTextView.swift`:放进类体里,不要放进 extension

`override` 不能写在非 `@objc` 的 extension 里,所以这段要写在类体内。

```swift
// MARK: - 选中高亮垂直居中

/// 把系统画的选中色块挪到"正好把文字包在正中"。
///
/// 行高倍数多出来的行距全堆在文字上方，UIKit 按整个行盒给矩形，
/// 所以色块上面空一大截、下面贴着字。这里把每个矩形**只平移、不改高度**，
/// 多行选中仍然首尾相接。
///
/// 位移 = 这一行字形盒的中心 − 系统矩形自己的中心（都换算到 container 坐标，
/// 差值与 inset、滚动偏移无关）。以矩形自身为基准，所以不依赖
/// `layoutFragmentFrame` 是否含段距。
override func selectionRects(for range: UITextRange) -> [UITextSelectionRect] {
    let rects = super.selectionRects(for: range)
    guard renderer.theme.lineHeightMultiple > 1,
          textStorage.length > 0,
          let layoutManager = textLayoutManager,
          let contentStorage = layoutManager.textContentManager as? NSTextContentStorage
    else { return rects }

    let documentStart = contentStorage.documentRange.location
    // 同一行的矩形位移相同：一次调用内按行缓存，长选区不重复量
    var shiftByRow: [Int: CGFloat] = [:]

    return rects.map { item in
        let box = item.rect
        guard !box.isNull, !box.isInfinite, box.height > 0 else { return item }

        // view 坐标 → container 坐标（扣掉 inset）
        let point = CGPoint(x: box.midX - textContainerInset.left,
                            y: box.midY - textContainerInset.top)
        let row = Int((point.y * 2).rounded())

        var shift: CGFloat
        if let cached = shiftByRow[row] {
            shift = cached
        } else {
            shift = glyphCenteringShift(at: point,
                                        layoutManager: layoutManager,
                                        contentStorage: contentStorage,
                                        documentStart: documentStart)
            shiftByRow[row] = shift
        }

        // 保险：位移不可能超过半个矩形高，超过说明量错了，宁可不动
        let limit = box.height / 2
        guard abs(shift) <= limit else { return item }
        guard shift != 0 else { return item }
        return ShiftedSelectionRect(base: item, rect: box.offsetBy(dx: 0, dy: shift))
    }
}

/// 某个矩形中心所在那一行，字形要下移多少才在矩形里垂直居中。
/// 不需要挪（没排好版、没套行高倍数、量不到字形、差不到 0.5pt）一律返回 0。
private func glyphCenteringShift(at point: CGPoint,
                                 layoutManager: NSTextLayoutManager,
                                 contentStorage: NSTextContentStorage,
                                 documentStart: NSTextLocation) -> CGFloat {
    // 没排好版的 fragment，行信息是空的、框也只是估算值，不碰
    guard let fragment = layoutManager.textLayoutFragment(for: point),
          fragment.state == .layoutAvailable else { return 0 }

    let start = contentStorage.offset(from: documentStart, to: fragment.rangeInElement.location)
    guard start >= 0, start < textStorage.length,
          // 图片 / 公式 / 表格占位故意没套行高倍数，别去挪它们
          let style = textStorage.attribute(.paragraphStyle, at: start, effectiveRange: nil) as? NSParagraphStyle,
          style.lineHeightMultiple > 1,
          let glyphs = textGlyphVerticalBounds(of: fragment, fragmentStart: start, nearestToY: point.y)
    else { return 0 }

    let shift = (glyphs.top + glyphs.bottom) / 2 - point.y   // 正 = 字在矩形中线下方，色块要下移
    return abs(shift) > 0.5 ? shift : 0
}

/// 一个"挪过的"选区矩形：位置换成新的，其余属性照抄原来的。
private final class ShiftedSelectionRect: UITextSelectionRect {
    private let base: UITextSelectionRect
    private let shifted: CGRect
    init(base: UITextSelectionRect, rect: CGRect) {
        self.base = base
        self.shifted = rect
        super.init()
    }
    override var rect: CGRect { shifted }
    override var writingDirection: NSWritingDirection { base.writingDirection }
    override var containsStart: Bool { base.containsStart }
    override var containsEnd: Bool { base.containsEnd }
    override var isVertical: Bool { base.isVertical }
}
```

和你原来那版相比,主要有这几处不同:

- **只量被选中的那一行**,不再用整段的字形范围。
- **以矩形自身中心为基准**,不再用 `layoutFragmentFrame` 的中心。
- **不再用 `closestPosition` 反查字符**,改用 `textLayoutFragment(for: CGPoint)`,避免在段落边界落到相邻段。
- **只处理套了行高倍数的段落**,图片、公式、表格占位不会被挪。
- **同一行只算一次**,位移超过半个矩形高就放弃,还没排好版的 fragment 也直接跳过。

# 大白话版

## 先说一个总比喻

把**行盒**想成一个高度为 34 厘米的相框，文字是相框里的一张 20 厘米高的照片，**照片贴在相框底部**，上方空出 14 厘米。

系统的选中色块，相当于**把整个相框涂成蓝色**，于是照片上方一大片蓝、下方只贴着一点点蓝，看起来文字偏下。

[selectionRects(for:)](file:///Users/pan/Project/iOSDemo/MarkdownEditorHy4/MarkdownEditor/Editing/MarkdownTextView.swift#L1071) 这段代码做的事情只有一件：

> 它并不会移动文字，只把蓝色色块整体往下挪 6.58 点，让照片在色块里上下留白相等。

---

## 一、为什么多出来的行距“全堆在文字上方”

先看系统实际量出来的数字（17 磅字体，1.7 倍）：

```
自然行高（1.0 倍）：行盒 20 点
y=0     ┌──────────────────┐
        │ 照片 Ag           │  ← 字几乎占满整个盒子
y=20    └──────────────────┘
        基线在 y=16

1.7 倍：行盒 34 点
y=0     ┌──────────────────┐
        │                  │
        │                  │  ← 多出来的 14 点，全在这里
        │                  │
y=14    │──────────────────│
        │ 照片 Ag           │  ← 字还是 20 点高，原样贴在底部
y=34    └──────────────────┘
        基线从 16 沉到了 30（正好 +14）
```

关键：**基线跟着行盒一起往下沉了 14 点，文字本身没有变大，也没有往上移**。因此 `lineHeightMultiple` 的效果可以理解为“把行盒加高、让基线往下沉”，它**并不会**把多出来的空间上下均分。

这也解释了为什么不能简单地把“行距”理解成“行与行之间的空隙”：多出来的 14 点确实落在这一行的顶部，也就是上一行文字和本行文字之间。

---

## 二、系统默认给的选中色块

你选中一行时，UIKit 直接拿**整个行盒**当色块：

```
系统给的 rect（container 坐标，y 从 0 到 34）

y=0     ┌──────────────────┐  ← 色块上沿
        │                  │
        │   （空 13.56）    │
        │                  │
y=13.56 │──── 文字上沿 ─────│
        │    正文 Ag        │  ← 字高约 20
y=33.59 │──── 文字下沿 ─────│
y=34    └──────────────────┘  ← 色块下沿，只空 0.41
```

用一句话说：**色块把相框涂满了，但照片是贴着底的**。

而你想要的效果是：

```
目标（文字在色块里上下留白相等）

y=6.58  ┌──────────────────┐
        │   （空 6.98）     │
y=13.56 │──── 文字上沿 ─────│
        │    正文 Ag        │
y=33.59 │──── 文字下沿 ─────│
y=40.58 └──────────────────┘
        │   （空 6.99）     │
```

上下留白都是约 6.98 点，文字就在正中间了。

---

## 三、代码的核心思路：只比“两个中心”

代码并不去计算“该挪多少”，只问一个问题：

> **文字的中心在哪里？色块的中心在哪里？把色块中心挪到文字中心上。**

写成公式：

```
位移 shift = 文字中心 y − 色块中心 y
```

代入实际数字：

```
文字中心 = (13.56 + 33.59) / 2 = 23.58
色块中心 = (0 + 34) / 2       = 17.00
shift = 23.58 − 17.00 = +6.58   （iOS 里 y 往下变大，正数 = 往下挪）
```

挪完以后：
- 上方留白 = 13.56 − 6.58 = 6.98
- 下方留白 = 40.58 − 33.59 = 6.99

正好相等。

**为什么不直接挪 `14 / 2 = 7`？** 此处只是巧合，因为这一行的字形上下留白不算特别不对称。真实情况里，如果一行里有脚注上标、行内公式图片，字形盒会偏向一边；代码按“中心对中心”计算，才能自动处理这些不对称。这也是代码注释里那句“以矩形自身为基准”的意思。

## 四、逐段拆代码

### 4.1 入口：没有调行高就原样返回

```swift
let rects = super.selectionRects(for: range)
guard renderer.theme.lineHeightMultiple > 1,
      textStorage.length > 0,
      let layoutManager = textLayoutManager,
      let contentStorage = ... else { return rects }
```

- 先把系统画好的矩形拿过来（`super`）。
- 用户没调行高（≤ 1 倍）时，行盒本来就贴着文字，**无需任何处理**，直接返回，性能最好。
- 后面两个 `let` 是用来做测量的工具：没有它们就量不到文字位置。

### 4.2 坐标换算：为什么只减 `inset`，不减滚动偏移

```swift
let point = CGPoint(x: box.midX - textContainerInset.left,
                    y: box.midY - textContainerInset.top)
```

这里有两套坐标：

```
text view 的内容坐标
┌────────────────────────────┐
│  inset.top = 16             │
│    ┌────────────────────┐   │ ← container 坐标的 (0,0) 在这里
│    │ 第一行行盒           │   │
│    │                    │   │
│    └────────────────────┘   │
│    ┌────────────────────┐   │
│    │ 第二行行盒           │   │
│    └────────────────────┘   │
└────────────────────────────┘
```

- `super.selectionRects` 给的是 **text view 内容坐标**（包含内边距）。
- `textLayoutFragment(for:)` 要的是 **container 坐标**（已经去掉内边距）。
- 所以把矩形中心减掉 `inset.left / inset.top`，两者就对齐了。

滚动偏移不用减，因为这两个都是“内容坐标”，内容在文档里的位置不会因为滚动而变。注释里说“差值与 inset、滚动偏移无关”，就是这个意思。

### 4.3 按行缓存：同一行的多个矩形只量一次

```swift
let row = Int((point.y * 2).rounded())
...
if let cached = shiftByRow[row] { shift = cached }
else { shift = glyphCenteringShift(...); shiftByRow[row] = cached }
```

一次选中可能返回很多个矩形（比如选中跨了好几行，或者系统把一行拆成了几块）。**同一行上的矩形，位移一定相同**，所以量一次、存起来。

`y * 2` 是把坐标量化到 0.5 点一格：同一行的矩形中心即使差零点几，也会落进同一个 key。这样能省掉重复测量，拖动选择时也更顺。

### 4.4 真正算位移的函数

```swift
private func glyphCenteringShift(at point: CGPoint, ...) -> CGFloat {
    guard let fragment = layoutManager.textLayoutFragment(for: point),
          fragment.state == .layoutAvailable else { return 0 }
```

- `textLayoutFragment(for:)`：问“这个点落在哪个段落块里”。
- `state == .layoutAvailable`：这个段落还没排好版时，量出来的是估算值，**宁可不挪**。

```swift
    let start = contentStorage.offset(from: documentStart, to: fragment.rangeInElement.location)
    guard ... let style = textStorage.attribute(.paragraphStyle, at: start, ...),
          style.lineHeightMultiple > 1,
          let glyphs = textGlyphVerticalBounds(of: fragment,
                                               fragmentStart: start,
                                               nearestToY: point.y)
    else { return 0 }
```

- 读这个段落的样式。图片、公式块这些段落**故意没套行高**，这里就会跳过它们。
- `nearestToY`：一个段落可能折成好几行，这个参数让函数只量“离当前矩形最近的那一行”，不会拿第一行来算第三行的位移。

```swift
    let shift = (glyphs.top + glyphs.bottom) / 2 - point.y
    return abs(shift) > 0.5 ? shift : 0
```

- 前半句就是“文字中心 − 色块中心”。
- 差不到 0.5 点就不挪：肉眼看不出来，还能少创建一个对象。

### 4.5 量字形：`textGlyphVerticalBounds` 在量什么

它在 [MarkdownTextView+Decorations.swift:403](file:///Users/pan/Project/iOSDemo/MarkdownEditorHy4/MarkdownEditor/Editing/MarkdownTextView%2BDecorations.swift#L403)，做三件事：

1. **找基线**：`基线 = fragment 顶部 + 这一行的行盒偏移 + glyphOrigin.y`
   实测 1.7 倍时 `glyphOrigin.y = 30`，所以基线在 30。
2. **往上往下量**：
   - 上沿 = 基线 − `font.ascender` = 30 − 16.44 = **13.56**
   - 下沿 = 基线 + |`font.descender`| = 30 + 3.59 = **33.59**
3. **取这一行里最大的字体度量**：一行里可能混着正文、代码、脚注上标，遍历每个字符，取最大的 ascender / descender；图片这类附件则按 `attachment.bounds` 算。

所以它量的是“**这一行真正画出来的东西**”，而不是“字体名义上的 `lineHeight`”。这也是为什么不能偷懒用 `font.lineHeight` 代替。

### 4.6 安全阀和包装类

```swift
let limit = box.height / 2
guard abs(shift) <= limit else { return item }
guard shift != 0 else { return item }
return ShiftedSelectionRect(base: item, rect: box.offsetBy(dx: 0, dy: shift))
```

- **安全阀**：位移不可能超过半个矩形高。超过说明量错了（比如拿错了行），宁可不动，也不让色块飞走。
- **包装类**：`UITextSelectionRect` 的 `rect` 是只读的，改不了；所以子类化一个 `ShiftedSelectionRect`，除了 `rect` 换成新位置，其余属性（`containsStart`、`containsEnd`、`isVertical`、`writingDirection`）原样抄。这几个属性关系到选区两端的圆形拖拽手柄，不能丢。

### 例 2：选中两行

系统给两块**紧挨着**的矩形（0~34、34~68），代码给两块都挪同样的 +6.58：

```
y=6.58  ┌──────────────┐
        │   第一行空 6.98│
y=13.56 │── 第一行文字 ──│
y=33.59 │── 第一行下沿 ──│
```

- 第二行文字中心 = (47.56 + 67.59) / 2 = 57.58
- 第二块矩形中心 = (34 + 68) / 2 = 51

> 如果按字形高度把每块都压成 20 点，两块之间就会露出 14 点的空隙，选中色块变成一条一条的斑马线。代码注释里的“多行选中仍然首尾相接”说的就是这个。

## 六、几个容易卡住的点

**Q1：这个函数会不会把文字挪了？**
不会。它只把“返回给 UIKit 的色块矩形”换个位置，文字排版一点没变，复制粘贴、光标、光标拖动都不受影响。

**Q2：为什么默认 1.0 倍时直接返回？**
因为行盒本来就贴着文字，计算出来的 shift 接近 0。提前返回既省性能，也保证“用户没调行高时，选中效果和系统原生一模一样”。

**Q3：为什么图片、公式块不挪？**
它们的段落样式**故意没写行高倍数**（图片占位自己算高度）。`style.lineHeightMultiple > 1` 这个判断会把它们挡掉，和 `caretRect` 里的理由一样：按全局值去挪，反而会把本来正常的色块挪歪。

**Q4：为什么正数表示往下挪？**
iOS 的 y 轴向下增长。文字的 y 比色块中心大（字在下方），所以 shift 是正的，矩形 `offsetBy(dy: shift)` 就是往下。

**Q5：为什么用中心相减，不分别算上下留白？**
中心相减只有一行加法，而且天然兼容各种不对称：字体度量不对称、一行里混了大字号、有行内图片。分别算上下留白就得写两套判断，还容易在附件上出错。

## 七、一句话总结

> 系统按“整个高行盒”画选中色块，所以上面空一大截；这段代码量出文字真正的上下沿，把色块**整体往下挪半个空隙**（实测 6.58 点），让文字中心和色块中心重合。文字不动，只动高亮。
