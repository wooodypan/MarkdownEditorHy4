按住 Option 再按上下箭头，整行搬家

新增了两条快捷键。按住 Option 再按 ↑，光标所在的这一行和上面那一行换个位置；按 ↓ 就是和下面那一行换。光标跟着这一行走，停在第几列也不变。

系统给这两个键的默认含义是「跳到上一段 / 下一段」，动的是光标。这里要的是 VS Code 那一套，动的是源码，所以自己接了过来。

搬的是整行，`# 标题` 这样的行连行首那个 `#` 一起走，不会把标记留在原地让下一行顶上。已经在第一行还按 ↑、或者已经在最后一行还按 ↓，就什么都不发生。这一下编辑走的是标准管线，⌘Z 一次就能退回来。

## 换行符为什么不跟着内容走

每一行末尾那个换行属于这一行自己占的槽位，交换的是两行的内容，槽位留在原处。

这个细节平时看不出来，碰到「文档最后一行没有换行」就会露馅。`AAA` 换行 `BBB`，末尾没有换行，把 `BBB` 往上搬，正确的结果是 `BBB` 换行 `AAA`。要是把换行当成内容的一部分跟着搬，就会拼出两行粘在一起、或者末尾凭空多一个空行的结果。

## 落在哪些文件

两条快捷键加在 `MarkdownTextView+Formatting.swift` 里那份清单上，和 ⌘B、⌘1~⌘6 那些放在一起。搬家本身是同一个文件里的 `moveCurrentLine(by:)`，`-1` 是上移、`1` 是下移。

清单里每一条都带一个标题，按住 ⌘ 时系统弹出的快捷键面板上写的就是这几个字，用户靠它才知道有这些快捷键。

## Mac 上按了没反应

上一版写完，我在文末留了一句「真机上按一下才知道」。你按了，没反应。

原因在系统那一层。macOS 的文本系统很早就把 ⌥↑ / ⌥↓ 定成了「跳到上一段 / 下一段」，这两个键是它自带的文本编辑命令，排队排在我们的快捷键前面。光标一进编辑器，按键先被它当成「移动光标」处理掉，`UIKeyCommand` 里那两条命令一次都没轮到。iPad 外接键盘没有这套绑定，那边一直是好的。

修法分两步。第一步给这两条命令打开 `wantsPriorityOverSystemBehavior`，这个开关的头文件注释写的就是「快捷键和焦点、文本编辑这类系统命令撞车时，要不要优先执行我们的」，默认关着。第二步在 `pressesBegan` 里再兜一道，按键真落到响应者手上时认一次，认出来就搬行，并把这次按键吃掉。

两道都在，因为它们管的是两层不同的事。第一道管系统命令的优先级，第二道管按键派发。任何一道生效就够了；两道同时生效也不会搬两次，快捷键命中时 UIKit 不会再把同一次按键往下派。

搬不动的时候两道都放手。光标已经在首行、或者文档是只读的，按下去什么都不会改，这时候把按键还给系统，「跳到上一段」照旧能用，用户不会觉得这是个死键。

认的是 HID 键码（↑ 是 0x52，↓ 是 0x51）。字符属性在不同键盘布局下会变，还可能被输入法吃掉，键码不会。⌥⌘↑ 和 ⌃⌥↑ 要排掉，它们在系统里另有含义。

## 没走 AppKit 那条路

也想过拦在更前面。项目里有一篇拦 ⌘W 的笔记，用的办法是运行期按名字把 AppKit 找出来装 `NSEvent` 事件监视器，那篇还专门拉了 Dynamic 这个库。这条路的麻烦在于 Catalyst 下 `NSEvent` 编译期根本不可见，同在 AppKit 里的 `NSCursor` 倒是可见（换鼠标指针那段就在用它），要拿只能运行期找，还得自己拼 block。既然 UIKit 自己的开关能解决问题，就没必要上那一套。真到要上的那天，那份笔记是现成的地图。

## 怎么保证它不会再犯

新加了 `MarkdownMoveLineTests`，十九条用例。前九条比的是源码搬完之后长什么样，上移、下移各一条，第一行和最后一行各一条（按了不动），末尾没有换行那两种情形各一条，另外守光标跟着这一行走、以及带语法标记的行整行一起搬。

后面几条守的是按键这一头。认键认对了没有，⌘ 和 ⌃ 的组合有没有被误认，搬不动的时候有没有把按键还回去，这些在模拟器上就能验。Mac 那两道闸本身验不了（Mac 上的测试进程这一阵起不来），能验的是它们共用的那份判据，以及「两条命令都开了优先级」这件事。

剩下一点还是要你在真机上按一下。按住 ⌥ 再按 ↑，看这一行有没有真的换到上面去。
