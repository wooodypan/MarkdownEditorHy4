按一下回车，代码块背景为什么会晚几百毫秒才跟上

在代码块上面按一下回车，整块内容往下挪了一行，灰底却先赖在原地，过几百毫秒才啪地跳下去。引用竖条、引用那层淡底色、任务列表的复选框，一个德性。

量出来的数（模拟器，420×800 的编辑器，在 `AAA` 后面敲一个回车）

| 装饰 | 按完回车当场量到 | 0.6 秒后的真值 |
| --- | --- | --- |
| 代码块灰底上沿 | 122.0 | 158.0 |
| 引用竖条上沿 | 215.1 | 263.1 |
| 复选框上沿 | 319.2 | 353.2 |

当场那个数比按回车之前还小一点（之前是 124.0），对不上任何一版排版，是 TextKit 在排版还没做时顺手给的估算值。

## 慢的那一拍卡在哪

代码在改完文本之后紧接着做了三件事，在 `MarkdownTextView.swift` 的 `applyEdit` 末尾

```swift
setNeedsLayout()
updateCodeBlockDecorationsIfNeeded(nearViewportOnly: true)
scheduleDecorationSettle()
```

第二件是当场重算视野附近的装饰坐标，第三件是等打字停下来（0.3 秒）再整篇重算一次。用户看到的那个「啪」，是第三件干的。

第二件白干了，因为它问早了。TextKit 2 改完文本只是先记一笔「这块待会儿要重排」，并**不会**立刻真的重排。这时候去问它 fragment 在哪儿，答的是回车之前的旧坐标，哪怕传了 `.ensuresLayout`。装饰就照旧坐标贴回老地方，只能等下一次重算才归位。

## 四个候选，量过才敢选

四种办法各单独跑一遍，看当场量到的数能不能对上 0.6 秒后的真值

| 办法 | 当场量到的代码块上沿 |
| --- | --- |
| 什么都不做 | 122.0 |
| `invalidateLayout(for:)` | 122.0 |
| `ensureLayout(for:)` | 158.0 |
| `textViewportLayoutController.layoutViewport()` | 158.0 |
| `layoutIfNeeded()` | 158.0 |

`invalidateLayout` 只作废不重排，量出来照样是旧的，等于白做。`layoutIfNeeded` 能生效，但它会把整篇重算那一趟也带起来，而打字这条路径特意只要视野附近，每敲一个字都整篇重排，长文档上肉眼看得见地卡。`layoutViewport()` 正是 TextKit 自己在布局那一轮里干的事，只排视口这一片，代价最小。

最后选了它。改动一共两处，`applyEdit` 里多出来一行调用，加上 `MarkdownTextView+Decorations.swift` 里的新函数

```swift
func flushPendingTextKitLayout() {
    textLayoutManager?.textViewportLayoutController.layoutViewport()
}
```

## 怎么保证它不会再犯

新加了 `MarkdownDecorationSettleLagTests`，四条用例。它们不管坐标具体是多少，只比两个数，改完当场量到的，和打字停下之后整篇重算出来的真值。

把上面那一行调用注释掉，其中三条立刻红，红出来的差正好是表里那三组数（122 对 158，215 对 263，319 对 353）。第四条是对照组，不编辑的时候坐标不该自己动。

全量单测 586 条，失败的 7 处还是复选框和表格横滚那几个老面孔，跟这次无关。

## 还剩一处没动

屏幕外的块不受这一行影响。它们本来就用估算坐标，要等滚进视野附近才重算，或者等 0.3 秒那次整篇重算兜底。这是刻意留的，每敲一个字都把整篇排一遍太贵。真机上打字时看得见的那一屏，现在改完当场就跟上。
