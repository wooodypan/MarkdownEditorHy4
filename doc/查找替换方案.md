## 查找替换到底包含哪三件事

```
用户在查找框输入 "hello"
        │
        ▼
① 在 source 里找出所有匹配位置 ← 「查找算法」这一步
        │
        ▼
② 把匹配位置在编辑器里高亮显示、导航到下一个/上一个 ← 「显示与定位」这一步
        │
        ▼
③ 用户点"替换"或"全部替换" ← 「执行替换」这一步,本质是编辑操作
```

这三步看起来是一条流水线,但它们"会不会被换掉"的答案完全不一样。

## 逐块判断

### ① 查找算法——值得做协议,理由和代码高亮一样

最朴素的实现是"子串精确匹配",暂时不做"忽略大小写"、"正则表达式"、"全词匹配"。今天用最简单的子串匹配跑起来,以后想换成支持正则的实现,不应该动到编辑器内部代码。

```swift
/// 与代码高亮协议是同一种设计思路:纯函数、不依赖 UIKit、不知道渲染细节
public protocol MarkdownSearching {
    /// 在 source 全文里找出所有匹配,返回 source 坐标系的区间。
    /// 注意:永远在 source 上搜索,不是在 NSAttributedString 上搜索——
    /// 原因和你复制粘贴那次的道理完全一样(第 9 节):source 才是唯一真源,
    /// 显示文本里混有图片/表格附件这类 synthetic 字符,直接在显示文本上搜索
    /// 既多余又容易把附件占位符误当成正文字符去匹配。
    func find(query: String, in source: String, options: SearchOptions) -> [Range<String.Index>]
}

public struct SearchOptions {
    public var caseSensitive: Bool = false
    public var wholeWord: Bool = false
    public var useRegex: Bool = false
}
```

默认实现给一个最朴素的版本就够用:

```swift
struct PlainTextSearcher: MarkdownSearching {
    func find(query: String, in source: String, options: SearchOptions) -> [Range<String.Index>] {
        guard !query.isEmpty else { return [] }
        var results: [Range<String.Index>] = []
        var searchStart = source.startIndex
        let compareOptions: String.CompareOptions = options.caseSensitive ? [] : [.caseInsensitive]

        while let range = source.range(of: query, options: compareOptions, range: searchStart..<source.endIndex) {
            results.append(range)
            searchStart = range.upperBound
        }
        return results
    }
}
```

以后想加正则,新写一个 `RegexSearcher: MarkdownSearching` 就行,装配时换一行,和代码高亮的接入方式一模一样,不用我再重复讲一遍——你已经会了。

### ② 高亮匹配、定位导航——**不值得**做协议,应该直接写在编辑器内部



"把匹配到的字符区间在文本里高亮显示"这件事,唯一合理的实现方式就是——给对应字符加背景色 attribute、滚动到可见位置。这不是一个存在"多种可互换算法"的环节,它是**编辑器显示能力的直接延伸**,和"怎么画引用竖条"是同一类问题(你架构文档第 7.3 节已经确认过:竖条怎么画不做协议,直接写在 `MarkdownTextView` 里)

```swift
// 直接是 MarkdownTextView 自己的方法,不经过任何协议
extension MarkdownTextView {
    func highlightSearchMatches(_ sourceRanges: [Range<String.Index>], currentIndex: Int?) {
        // 复用你已有的 DisplaySourceMap(第 9.2 节),
        // 只是这次用的是"source → display"方向,跟第 8 轮"点击目录跳转"用的是同一个映射,同一份代码
        let displayRanges = sourceRanges.compactMap { documentController.displayRange(forSourceRange: $0) }

        textStorage.beginEditing()
        for (index, range) in displayRanges.enumerated() {
            let isCurrent = index == currentIndex
            textStorage.addAttribute(.backgroundColor,
                value: isCurrent ? theme.colors.searchMatchCurrent : theme.colors.searchMatchOther,
                range: range)
        }
        textStorage.endEditing()

        if let currentIndex, displayRanges.indices.contains(currentIndex) {
            scrollRangeToVisible(displayRanges[currentIndex])
        }
    }
}
```



### ③ 执行替换——同样不值得做协议,直接复用你已有的编辑管线

替换的本质是"把 source 里某段文字换成另一段文字",这和你在任务列表那一轮(点击复选框)得出的结论**一模一样**:不要为这个动作发明新的修改文档方式,翻译成一次标准编辑,直接调用 `applyEdit`。

```swift
extension MarkdownDocumentController {
    func replace(range: Range<String.Index>, with replacement: String) {
        _ = applyEdit(sourceRange: range, replacementText: replacement)  // 复用第 11 节的增量管线,撤销/重做自动生效
    }

    /// 全部替换:一个新手很容易踩的坑在这里——见下方"性能与正确性提示"
    func replaceAll(_ ranges: [Range<String.Index>], with replacement: String) {
        for range in ranges.sorted(by: { $0.lowerBound > $1.lowerBound }) {
            // 必须从后往前替换!否则前面替换完,后面匹配位置记录的 String.Index 全部失效
            _ = applyEdit(sourceRange: range, replacementText: replacement)
        }
    }
}
```

## 给新手的判断口诀

这次拆解出的规律,其实就是上一轮我们已经用过的检验标准,这里把它写成一个可以直接套用的检查清单:

| 问自己 | 是 → 做协议 | 否 → 直接写在编辑器内部 |
|---|---|---|
| 这一步存在"多种互斥的合理实现",而且用户/开发者可能真的想换? | 查找算法(子串/正则/模糊) | —— |
| 这一步是"把已有结果显示出来"或"复用已有的显示/编辑能力"? | —— | 高亮匹配、滚动定位、执行替换 |
| 做协议后,协议方法的参数/返回值需要泄露具体实现细节(比如返回 NSAttributedString、暴露某个第三方库的类型)? | 需要重新设计成中性类型(比如上次的 `SyntaxRole`) | 不做协议,细节留在内部反而更简单 |
| 抽象出来的这层,会不会只有你自己一个实现,且预期永远只有一个? | —— | 不值得,直接写死 |

用这张表回头看代码高亮那次:查找算法和"要不要高亮 keyword"是同一类判断——**算法选择**该抽象;而"竖条怎么画""替换怎么执行"是**已确定的实现细节**,不该抽象。这也是为什么这次答案不是"整体解耦"或"整体不解耦",而是把一个功能拆开、分别判断——这才是你该学会的能力,不是记住"查找替换要不要解耦"这一个孤立答案。

## 查找框 UI 本身:复用目录组件那一套模式,而不是代码高亮那一套

容易漏掉的一点:你问的是"查找替换"要不要解耦,但**查找框本身也是一个独立 UI 组件**(输入框、上一个/下一个按钮、替换输入框、全部替换按钮),这部分不属于上面①②③里任何一个,它对应的是第 8 轮"目录组件解耦"的模式——**协调者 + 双方只认协议**,而不是代码高亮的"可插拔算法"模式:

```swift
protocol MarkdownSearchDataSource: AnyObject {
    func performSearch(query: String, options: SearchOptions) -> Int   // 返回匹配总数
    func jumpToMatch(at index: Int)
    func replaceCurrentMatch(with text: String)
    func replaceAllMatches(with text: String)
}

protocol MarkdownSearchBarDisplaying: AnyObject {
    func updateMatchCount(current: Int, total: Int)
}

final class SearchCoordinator {
    weak var editorDataSource: MarkdownSearchDataSource?
    weak var searchBar: MarkdownSearchBarDisplaying?
    // 结构和 OutlineCoordinator 完全一致,不再重复展开
}
```

`MarkdownTextView` 实现 `MarkdownSearchDataSource`,`MarkdownFindBarView`(新写的查找框 UI)实现 `MarkdownSearchBarDisplaying`,两者互不引用——这部分请直接照搬第 8 轮 `OutlineCoordinator` 的结构,是同一个模式的第二次应用,不需要我再重新讲一遍原理。

## 性能提示(既然你每次都要求高性能,这里点两个新手常忽略的点)

1. **查找不要每次按键都全文重搜**:用户在查找框打字是高频事件,和目录组件"光标移动要防抖"是同一个道理(第 8 轮已经讲过),这里同样加一个 100-150ms 的防抖,并且把 `find(query:in:options:)` 放到后台线程执行(`source` 是不可变值类型,天然线程安全,跟你架构里"解析可以放后台"的理由完全一样)。

2. **高亮匹配不要一次性处理全文档的匹配结果**:如果文档很长、匹配到几百处,不需要把几百个 `backgroundColor` attribute 一次性全加上——复用你架构文档第 12.2 节"视口优先渲染"的思路,只优先给当前可见范围内的匹配上色,滚动到别处时再补,这样长文档下查找不会有明显卡顿。

3. **全部替换必须倒序处理**(上面代码已经写了,但值得单独强调,这是新手最容易踩的坑):正序替换会导致后面每一处匹配记录的 `String.Index` 因为前面文字长度变化而全部失效,必须从文档末尾往前替换,这样已处理区间之外的坐标不受影响。

## 一句话总结给新手

**不是"像代码高亮一样做协议"就是架构进步,协议只该用在"真的存在可互换实现"的地方。** 查找替换里,算法是可互换的(做协议),显示和编辑执行不是可互换的(直接复用已有机制),UI 组件是需要独立替换的(用协调者模式,不是可插拔算法模式)——一个功能同时用到三种不同的解耦策略,是完全正常的,不代表architecture不一致,恰恰说明你在用"这一小块该不该抽象"而不是"这个功能该不该抽象"来做判断,这才是正确的颗粒度。
