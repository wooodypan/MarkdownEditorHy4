> 我这个高性能的markdown编辑器想支持脚注，应该怎么实现？

Sonet 5 Extra：

脚注这个功能的特殊之处在于——它是整个对话里第一个**真正"跨块"的语法元素**。之前所有东西（图片、表格、代码块、引用、任务列表）都严格活在自己的顶层块内部，脚注不是：`[^1]` 这个引用标记可能出现在文档开头的段落里，它对应的定义 `[^1]: 这是脚注内容` 却可能在文档末尾，中间隔着几十个其他块。这对你整个架构里好几个已经定下的假设——尤其是"顶层块是增量解析的最小单元"（第 3.1 节）——是一次真正的考验，要先把这件事说透，再谈怎么做。

## 第一步：确认 swift-markdown 认不认识脚注

Swift Forums 上 DocC 团队的讨论明确说明在 QuietMisdreavus 的帮助下，swift-markdown 已经支持脚注解析，这需要对 swift-cmark 库做一些改动才能实现。它由两个元素组成：行内的 footnoteReference 和块级的 footnoteDefinition。两者都以 footnoteID 作为数据，footnoteDefinition 可以包含子元素。这确认了两件关键事实：① 节点类型是 `FootnoteReference`（行内）和 `FootnoteDefinition`（块级），② 两者通过一个共同的 `footnoteID` 关联——这正是接下来整个方案要围绕的核心。

## 为什么脚注要单独拎出来架构，不能照搬之前的模式

先说清楚这次和之前所有功能的本质区别，这是理解后续设计的前提：

| 之前的功能 | 脚注 |
|---|---|
| 图片、表格、代码块、引用——语法标记和它"管辖的内容"在**同一个顶层块内部**，渲染时一次遍历就能处理完 | `[^1]` 这个引用标记在正文段落里，`[^1]: 脚注内容` 这个定义块可能在文档完全不同的位置，**两者是通过 ID 关联、但物理位置分离的** |
| 一个顶层块的渲染不依赖其他块的内容 | 渲染 `[^1]` 这个引用标记时，**需要知道 `[^1]:` 这个定义块的内容**（至少要知道编号、可能还要在用户长按/点击时弹出定义的预览文字）——这是你架构里第一次出现"块间依赖" |
| 增量解析时，第 11.2 节的边界规则只需要考虑"这个块内部的改动会不会影响相邻块结构" | 脚注的增量解析要多考虑一种情况：**编辑了文档某处的脚注定义块，需要让文档中所有引用这个 ID 的地方重新渲染**（哪怕引用标记本身所在的段落一个字符都没改） |

这就是为什么脚注不能简单套用"顶层块独立渲染"的现成模式，需要在你的 `MarkdownDocumentModel` 上加一层**跨块索引**。

## 结论先行

**脚注定义（`[^1]: ...`）仍然是普通的顶层块（`BlockKind.footnoteDefinition`），按文档已有的增量渲染规则处理；脚注引用（`[^1]`）在正文里渲染成一个小的、可点击的上标编号，用一个独立维护的"ID → 定义块"索引表做关联，而不是在渲染每个引用时现场遍历全文找定义。点击引用标记跳转到定义处（或弹出悬浮预览），复用你已有的"目录跳转"那套 source↔display 坐标映射机制，不需要发明新的定位逻辑。**

## 具体设计

### 1. 新增跨块索引：`FootnoteIndex`

这是这次新增的唯一一块真正的新机制，挂在 `MarkdownDocumentModel` 上，和 `blocks` 数组同级：

```swift
/// 全文档范围的脚注 ID -> 定义块映射,随增量解析同步维护。
/// 这是你架构里第一个「跨顶层块」的索引结构——之前的 BlockID、DisplaySourceMap
/// 都是「同一个块内部」或「块本身」的概念,这个索引第一次需要跨越块的边界。
final class FootnoteIndex {
    private(set) var definitionsByID: [String: BlockID] = [:]      // "1" -> 定义块的 BlockID
    private(set) var referenceOrder: [String] = []                  // 按文档中「引用第一次出现」的顺序排列的 ID 列表,决定显示编号

    /// 每次全量或增量解析后调用,重建/更新受影响部分的索引
    func rebuild(from blocks: [MarkdownBlock]) {
        definitionsByID.removeAll()
        for block in blocks {
            if case .footnoteDefinition(let footnoteID) = block.kind {
                definitionsByID[footnoteID] = block.id
            }
        }
        // referenceOrder 的维护见下方「显示编号」部分
    }

    /// 给定一个脚注 ID,返回它应该显示的编号(按第一次被引用的顺序,这是 GFM 脚注的标准行为——
    /// 不是按定义出现的顺序,而是按引用出现的顺序编号)
    func displayNumber(for footnoteID: String) -> Int? {
        referenceOrder.firstIndex(of: footnoteID).map { $0 + 1 }
    }
}
```

**为什么编号要"按引用顺序"而不是"按定义顺序"**：这是 GFM 脚注的标准约定——用户可能把所有脚注定义统一写在文档末尾（常见写法），但编号 `[1]` `[2]` `[3]` 要按它们在正文里第一次被引用到的先后顺序显示，这也是为什么这个索引不能只是简单的字典，还要维护一个有序的 `referenceOrder` 数组。

### 2. 渲染阶段：`visitFootnoteReference` / `visitFootnoteDefinition`

```swift
mutating func visitFootnoteReference(_ ref: FootnoteReference) -> NSAttributedString {
    let footnoteID = ref.footnoteID
    let literalText = literalText(for: ref)  // 精确切出 "[^1]" 这几个字符,全字符保留原则不变

    let displayNumber = footnoteIndex.displayNumber(for: footnoteID) ?? 0
    let hasDefinition = footnoteIndex.definitionsByID[footnoteID] != nil

    let result = NSMutableAttributedString(string: literalText, attributes: [
        // 延续「全字符可见、只是弱化」原则——[^1] 原始字符保留但弱化,
        // 视觉上用上标编号来承载「这是第几个脚注」这个信息
        .foregroundColor: theme.colors.syntaxMarkerDimmed,
        .font: theme.typography.bodyFont,
    ])

    // 用上标 attribute 叠加显示编号,而不是像图片/表格那样插入新的附件字符——
    // 脚注引用标记很短,用「同一段字符、换一种排版方式」就够了,不需要上附件这种重机制
    result.addAttribute(.baselineOffset, value: theme.footnote.superscriptOffset,
                         range: NSRange(location: 0, length: result.length))
    result.addAttribute(.font, value: theme.typography.bodyFont.withSize(theme.footnote.markerFontSize),
                         range: NSRange(location: 0, length: result.length))
    if hasDefinition {
        result.addAttribute(.foregroundColor, value: theme.colors.link, range: NSRange(location: 0, length: result.length))
        result.addAttribute(.markdownFootnoteTarget, value: footnoteID, range: NSRange(location: 0, length: result.length))
    }
    return result
}

mutating func visitFootnoteDefinition(_ def: FootnoteDefinition) -> NSAttributedString {
    let footnoteID = def.footnoteID
    let displayNumber = footnoteIndex.displayNumber(for: footnoteID) ?? 0

    let result = NSMutableAttributedString()
    // 定义块本身的渲染和普通段落一样(复用 visitParagraph 等已有逻辑处理内部子节点),
    // 只是在开头加一个编号标记,并打上可被跳转定位的标记
    result.append(NSAttributedString(string: "[\(displayNumber)] ", attributes: [
        .foregroundColor: theme.colors.syntaxMarkerDimmed, .font: theme.typography.codeFont,
    ]))
    for child in def.children {
        result.append(visit(child))  // 复用现有的段落/加粗/列表等渲染逻辑,脚注定义内部支持的语法和引用块一样,不需要新代码
    }
    result.addAttribute(.markdownFootnoteDefinitionID, value: footnoteID,
                         range: NSRange(location: 0, length: result.length))
    return result
}
```

**关键点**：脚注引用标记**没有用附件**（不像图片/表格/公式那样插 `NSTextAttachmentViewProvider`），而是用"上标字体 + baselineOffset + 特殊颜色"这种纯 attribute 手段——这是因为脚注引用标记极短（通常只是一两位数字），用附件这种重机制反而是过度设计，用你自己总结的判断标准看：**这里不存在"需要真正的 View 才能表达"的内容**（不像图片需要异步加载、表格需要网格布局），纯文字排版完全够用。

### 3. 点击跳转：复用你已有的"目录跳转"机制，不发明新逻辑

这是整个方案里最值得强调的一点——点击脚注引用跳到定义处，和"点击目录项跳到标题处"（上几轮已经做完的功能）在技术上是**同一件事**：都是"给定一个目标位置的 source 坐标，转换成 display 坐标，滚动过去"。

```swift
extension MarkdownTextView {
    func handleTap(at location: CGPoint) {
        guard let footnoteID = footnoteTargetID(at: location) else { return }
        guard let definitionBlockID = documentController.footnoteIndex.definitionsByID[footnoteID],
              let definitionBlock = documentController.block(for: definitionBlockID) else { return }

        // 与 OutlineCoordinator.scrollToOutlineItem 完全同一套逻辑(第 8 轮方案第 4 节),
        // 只是目标坐标的来源从「OutlineItem.sourceOffset」换成了「脚注定义块的起始位置」
        let sourceOffset = definitionBlock.span.range.lowerBound
        guard let displayLocation = documentController.displayLocation(forSourceIndex: sourceOffset) else { return }
        let range = NSRange(location: displayLocation, length: 0)
        selectedRange = range
        scrollRangeToVisible(range)
        flashHighlight(at: range)
    }
}
```

**不需要重新设计坐标映射、不需要新的跳转动画逻辑**——这正是前几轮把"source↔display 坐标映射"做成一个独立可复用机制（而不是散落在各处写死）带来的直接收益,这是第三次复用到同一套底层能力了(第一次是代码块复制按钮,第二次是目录跳转,这次是脚注跳转)。

### 4. 增量解析：唯一真正需要新规则的地方

回到开头说的"跨块依赖"问题——第 11.2 节现有的边界扩展规则（"编辑发生在列表项内部→扩展到整个列表"这类）全部是**同块或相邻块**的局部判断，脚注需要一条新规则：

```swift
extension AffectedRangeCalculator {
    /// 新增规则:如果本次编辑触及的块是「脚注定义块」,且它的 footnoteID 在索引中,
    /// 需要额外标记「所有引用这个 ID 的块」为「需要重新渲染」(但不需要重新解析——
    /// 它们的 AST 结构没变,只是显示编号/链接目标可能变化)。
    func footnoteCascadeBlocks(affectedByEdit range: Range<String.Index>,
                                 blocks: [MarkdownBlock], index: FootnoteIndex) -> Set<BlockID> {
        let touchedFootnoteIDs = blocks
            .filter { $0.span.range.overlaps(range) }
            .compactMap { block -> String? in
                if case .footnoteDefinition(let id) = block.kind { return id }
                return nil
            }
        guard !touchedFootnoteIDs.isEmpty else { return [] }

        // 找出所有包含这些 ID 引用标记的块——这是一次性的、仅在命中脚注定义编辑时才触发的扫描,
        // 不是每次编辑都要做,性能影响仅限于「用户确实在编辑脚注定义」这个相对少见的场景
        return Set(blocks.filter { block in
            block.containsFootnoteReferences(to: Set(touchedFootnoteIDs))
        }.map(\.id))
    }
}
```

**这条新规则的触发频率很低**——只有当用户编辑的内容恰好落在某个 `FootnoteDefinition` 块内部时才会触发"级联重渲染"，日常的正文编辑（段落、列表、代码块）完全不会碰到这条路径，不会拖慢你架构整体的增量性能特征。另外要强调：**级联触发的是"重新渲染"，不是"重新解析"**——那些引用这个 ID 的块本身的 AST 结构完全没变（`[^1]` 这几个字符没动），只是它们依赖的"这个 ID 显示第几号、链接到哪"这个外部信息变了，所以只需要重跑 `BlockRenderer.render`，不需要重跑 `Document(parsing:)`，这是区分"解析"和"渲染"两个独立环节（你架构从一开始就坚持的分层）在这里第一次真正体现出价值的地方。

## 一个容易漏掉但必须处理的边界情况：悬空引用

用户完全可能写出 `[^1]` 但从未写 `[^1]: ...` 定义（打字打到一半、或者故意先占位），或者反过来定义了但没在正文任何地方引用。按你"全字符可见"的底线原则，**这两种情况都不应该报错或崩溃，只需要视觉上区分出来**：

- 悬空引用（有 `[^1]` 没有对应定义）：用 `danglingReferenceColor`（比如红色）标记，提示用户这是个"断链"，但字符本身正常显示、正常参与复制。
- 未被引用的定义（有 `[^1]:` 定义但正文没人引用它）：按 GFM 标准行为，这类定义通常不显示编号（因为编号是按引用顺序分配的，没被引用就没有编号），可以在视觉上用弱化灰色展示，或者完全不特殊处理、作为普通段落显示——这个属于产品细节选择，不影响架构。

## 需求与现有架构对照

| 需要的能力 | 复用哪部分已有设计 / 新增了什么 |
|---|---|
| 识别脚注语法 | swift-markdown 原生支持的 `FootnoteReference`/`FootnoteDefinition` 节点，不需要自己写解析逻辑 |
| 引用标记显示为上标编号 | 纯 `NSAttributedString` attribute（`baselineOffset`+字号），不需要像图片那样上 `NSTextAttachment` |
| 点击跳转到定义处 | **完全复用**目录组件(第 8 轮)已经建好的 source↔display 坐标映射和滚动跳转逻辑 |
| 全字符可见 | 延续贯穿全文档的原则，`[^1]` 字符保留，只是弱化+上标化 |
| 编号按引用顺序分配 | 新增 `FootnoteIndex`，这是本方案唯一真正新增的核心机制 |
| 增量渲染时跨块联动 | 新增一条边界规则（脚注定义变化→级联重渲染所有引用它的块），触发频率低，不影响整体增量性能 |
| 悬空引用的健壮性 | 视觉区分（红色），不报错、不崩溃，字符依然完整保留和可复制 |
