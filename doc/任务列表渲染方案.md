任务列表这个需求比前面几个多了一个新维度——**需要响应点击并写回 source**，这是你架构里第一次出现"渲染出的控件要反向修改文档内容"（图片/复制按钮的点击都不改 source，只是读取或触发副作用）。所以要单独说清楚这条数据流怎么走，不能简单套用图片附件的模式。

## 结论先行

**复选框本身用 `NSTextAttachmentViewProvider` 内嵌一个真正的 `UIButton`（勾选框样式），插入在 `[x]`/`[ ]` 这几个字符的位置上层叠显示；`[x]`/`[ ]` 原始字符仍然保留在文本流里但视觉上被复选框完全遮盖；点击复选框直接修改 `source` 里对应的那一个字符（`x`/`X`/空格），走你已有的增量编辑管线，而不是自己发明一套"UI 状态"。**

## 为什么是"遮盖"而不是"替换成图片附件+弱化文字"（和图片、表格不同的地方）

图片、表格的方案是"附件在上面、源码弱化文字在下面另起一行"，但任务列表不适合这样处理，原因：

- `[x]` 只有 3-4 个字符，是**行内的一部分**（`- [x] 已完成` 是同一行），不像图片/表格是独占的块级内容，没有"上方/下方"的空间关系可言。
- 用户会频繁点击切换状态，如果每次点击都要"新起一行显示状态"，交互上很别扭；直接原地是一个可点的勾选框才符合直觉（这就是几乎所有 Markdown 编辑器——Bear、Notion、Obsidian——任务列表的标准做法）。

所以这里的策略是：**复选框附件和 `[x]`/`[ ]` 文字共享同一段字符位置**（附件宽度精确等于这几个字符的宽度），视觉上完全遮盖住底下的文字，而不是插在文字上方另起一行。这跟你现有的"全字符保留、只做弱化"原则是一致的——字符依然在 `NSAttributedString` 里、依然会被复制到剪贴板，只是被一个不透明的附件盖住了显示位置。

## 具体设计

### 1. 渲染阶段：识别任务列表项，替换 `[x]`/`[ ]` 这几个字符为附件

swift-markdown 对 GFM 任务列表的支持是通过 `ListItem.checkbox` 属性（`Checkbox?` 枚举，`.checked`/`.unchecked`），不需要自己用正则去猜测 `[x]`/`[ ]` 语法：

```swift
mutating func visitListItem(_ listItem: ListItem, ordered: Bool, index: Int) -> NSAttributedString {
    let result = NSMutableAttributedString()

    // 先画列表圆点/序号（复用现有逻辑）
    result.append(renderMarker(ordered: ordered, index: index))

    if let checkbox = listItem.checkbox {
        // 精确定位 [x] / [ ] 在源码中的字符范围
        let checkboxSourceRange = checkboxLiteralRange(for: listItem)  // 从 range 取 "[x]" 或 "[ ]" 三个字符
        let checkboxText = String(sourceSlice[checkboxSourceRange])

        let attachment = MarkdownCheckboxAttachment(
            isChecked: checkbox == .checked,
            blockItemID: stableID(for: listItem),  // 稳定 ID，见下方"稳定标识"说明
            theme: theme
        )
        // 附件覆盖的字符范围 = [x]/[ ] 这几个字符本身（原样保留在字符串里，只是被附件盖住）
        let checkboxRun = NSMutableAttributedString(string: checkboxText, attributes: [
            .foregroundColor: UIColor.clear,   // 文字仍在，但透明——保证「全字符保留」不变量，
                                                 // 附件绘制在同一位置盖住视觉呈现
        ])
        checkboxRun.addAttribute(.attachment, value: attachment,
                                   range: NSRange(location: 0, length: 0))  // 见下方说明：真正做法用零宽附件+覆盖

        result.append(checkboxAttachmentRun(text: checkboxText, attachment: attachment))
    }

    // 剩余内容（"已完成" 这部分文字）
    for child in listItem.children where !(child is Paragraph && isFirstParagraphCheckboxLine) {
        result.append(visit(child))
    }
    return result
}
```

这里有个实现细节要讲清楚：**"文字透明 + 附件盖住"和"附件本身占位、文字完全移除"是两种做法，选哪种取决于你对"全字符保留"这条不变量有多严格**。

- **做法 A（推荐）**：`[x]` 三个字符保留在 `NSAttributedString` 里、`.foregroundColor` 设为 `.clear`（不可见但依然占据布局位置和字符序列位置），复选框附件作为**零宽度的 `NSTextAttachment`** 插入在这三个字符的正上方，用 `NSTextAttachmentViewProvider` 的 `attachmentBounds` 返回一个跨越这三个字符宽度的 frame（需要精确测量 `[x]` 在当前字体下的实际宽度）。这样字符序列长度和 source 完全一致，不需要在 `DisplaySourceMap` 里为任务列表新增任何特殊的 `synthetic` 处理规则。
- **做法 B（更简单但打破字符同构）**：直接删掉 `[x]` 三个字符，用一个固定宽度的附件字符代替，像图片附件一样标记为 `markdownSynthetic`。实现更简单，但复制时需要**从 `MarkdownCheckboxAttachment` 里读回它代表的原始文字**（`"[x]"` 还是 `"[ ]"`）重新拼回复制结果——这和你现有的"synthetic 字符复制时直接跳过"的规则不一致（因为跳过会导致复制结果丢失 `[x]` 这三个字符），需要给 `DisplaySourceMap` 加一种新的 segment kind：`syntheticButRepresents(text: String)`。

**建议用做法 A**，因为它不需要给复制机制引入新的分支逻辑，完全复用现有的"全字符保留、只是被遮盖"模型，代码一致性更好。唯一的成本是需要精确测量 `[x]` 三个字符在当前字体下的像素宽度来定位附件（用 `NSAttributedString.size()` 对这三个字符单独测量即可，不复杂）。

### 2. 点击交互：`UIButton` + 循环切换三态

你的需求是"点击后在 `[x]` 和 `[ ]` 之间循环切换"，但你给的例子里出现了大写 `[X]`，按 GFM 规范 `x`/`X` 都算"已完成"，所以循环逻辑应该是**二态循环**（未完成 ↔ 完成），点击时统一写回小写 `x`（不需要保留用户原来是大写还是小写——除非你想保留原始大小写风格，那是三态：`[ ]` → `[x]` → `[X]` → `[ ]`，但这个必要性不大，建议做二态）：

```swift
final class MarkdownCheckboxAttachmentViewProvider: NSTextAttachmentViewProvider {
    override func loadView() {
        let attachment = textAttachment as! MarkdownCheckboxAttachment
        let checkbox = MarkdownCheckboxButton(isChecked: attachment.isChecked, theme: attachment.theme)
        checkbox.onTap = { [weak self] in
            guard let self else { return }
            NotificationCenter.default.post(
                name: .markdownCheckboxToggled,
                object: nil,
                userInfo: ["itemID": attachment.blockItemID]
            )
            // 实际项目里建议用 delegate 或 Combine，这里用通知只是示意数据流方向
        }
        view = checkbox
    }

    override func attachmentBounds(for attributes: [NSAttributedString.Key: Any],
                                     location: NSTextLocation,
                                     textContainer: NSTextContainer?,
                                     proposedLineFragment: CGRect,
                                     position: CGPoint) -> CGRect {
        let size = theme.taskList.checkboxSize   // 例如 18×18
        return CGRect(x: 0, y: (theme.typography.bodyFont.lineHeight - size.height) / 2,
                      width: size.width, height: size.height)
    }
}
```

`MarkdownCheckboxButton` 本身是一个简单的自绘按钮（方框 + 打勾图标 + 点击态高亮），不需要用系统 `UISwitch`/`UIButton.Configuration` 那种重量级组件。

### 3. 点击后如何改 `source`：直接复用你的增量编辑管线，不要另开分支

这是最关键的一点：**复选框点击不应该有自己独立的"修改文档"逻辑，而应该翻译成一次标准的"文本替换"编辑，走第 11 节完整的增量解析渲染流程**——这样能保证：撤销/重做自动生效（因为走的是标准编辑路径）、复选框点击导致的变化会正确触发该 `MarkdownBlock` 的重新解析（虽然内容极简单，但保持路径一致，不给自己留特例）。

```swift
extension MarkdownDocumentController {
    func toggleCheckbox(itemID: BlockItemID) {
        guard let listItem = findListItem(itemID),
              let checkboxRange = checkboxSourceRange(for: listItem) else { return }

        let currentChar = source[checkboxRange]  // "x" / "X" / " "
        let newChar = (currentChar == " ") ? "x" : " "

        // 复用 applyEdit，走完整的「计算受影响块 → 局部重解析 → 局部重渲染」路径（第 11 节）
        _ = applyEdit(sourceRange: checkboxRange, replacementText: newChar)
    }
}
```

因为受影响范围只有 1 个字符，第 11.2 节的边界扩展规则会把它判定为"编辑发生在列表项内部 → 扩展到整个连续列表"（你架构文档里已有的规则），重新解析、重新渲染的范围是这一个列表块，成本很小，不需要为"复选框点击"单独设计一套更轻量的更新路径——保持架构一致性带来的收益大于这点性能差异。

### 4. 稳定标识：为什么需要 `blockItemID` 而不是用数组下标

因为增量渲染、拖拽排序都可能改变列表项在数组里的位置，点击回调里如果用"下标"定位会在异步场景下（比如点击后、渲染完成前用户又做了别的编辑）定位到错误的项。做法是给每个 `ListItem` 生成一个**基于其在 source 中位置派生的稳定 ID**（比如用它对应源码文本的哈希，或者渲染时按文档顺序分配的递增 ID，只要保证"同一个逻辑列表项在增量重渲染前后 ID 不变"即可），这个 ID 只在渲染层内部使用，不需要持久化。

### 嵌套任务列表（你例子里的第二个场景）

```
- [X] 大写 X 也表示完成
  - [ ] 嵌套任务
```

不需要任何特殊处理——`visitListItem` 本身就是递归调用的（子列表是 `ListItem.children` 里的一个嵌套 `UnorderedList`），缩进由列表本身的缩进机制处理（现有 `ListMarker.textIndent` 按嵌套深度累加，和引用块的分层缩进是同一个模式），复选框的渲染和点击逻辑对每一层的 `ListItem` 都一样，天然支持任意深度嵌套。

## 需要在 `MarkdownTheme` 里补的配置

```swift
struct TaskList: Equatable {
    var checkboxSize: CGSize = .init(width: 18, height: 18)
    var checkboxCornerRadius: CGFloat = 4
    var checkedColor: UIColor = .systemGreen        // 与列表圆点绿色呼应，视觉统一
    var uncheckedBorderColor: UIColor = .separator
    var checkedTextStrikethrough: Bool = true        // 常见交互反馈：完成项加删除线（可选）
    var checkedTextColor: UIColor = .secondaryLabel  // 完成项文字弱化（可选）
}
```

`checkedTextStrikethrough`/`checkedTextColor` 是否要做，取决于产品是否希望"勾选后文字视觉上也变化"（很多编辑器会这样做），如果要做，加删除线这类 attribute 只作用于"已完成"复选框对应的那段正文文字，不影响复选框本身的渲染逻辑，两者可以独立开关。

## 和现有架构的复用关系一览

| 需要的能力 | 复用哪部分 |
|---|---|
| 复选框作为可点击控件嵌入文本流 | 与代码块复制按钮同一套 `NSTextAttachmentViewProvider` 机制 |
| 字符保留、只是视觉遮盖 | 延续"全字符可见"原则的一个新变体（透明色+附件覆盖，而非插入新字符） |
| 点击后修改文档 | 直接复用 `applyEdit` 增量编辑入口，不新增编辑路径，天然获得撤销/重做和增量渲染 |
| 嵌套任务列表缩进 | 复用列表嵌套缩进机制，无需新代码 |
| 复制时不带复选框 UI | 因为附件不是插入字符（做法 A），复制天然只会复制到原始 `[x]`/`[ ]` 字符，不需要新的 `DisplaySourceMap` 规则 |

## 实际实现（2026-09-18 更新，以代码为准）

上面是**动手前的方案**，落地时改了不少。这里记一份实际形态，免得后来人照着上面的示例代码去改。

### 和方案的三处偏离

| 方案里写的 | 实际做的 | 为什么 |
|---|---|---|
| 用 `NSTextAttachmentViewProvider` 把真 `UIButton` 嵌进文本流 | 文本流里只留**座位**，真正的 `UIButton` 由 `MarkdownTextView` 叠上去 | 本项目在图片上实测过 view provider 的坑：整篇替换内容后 TextKit 2 会把 attachment 的 view 摘掉、**不再回调 `loadView()`**，view 永久消失（见 skill `ios-textkit2-attachment-pitfalls`） |
| `[x]` 三字符保留但 `.foregroundColor = .clear`，附件盖住 | 三字符**照常可见**（浅灰），另外插一个**透明座位**给按钮腾位置 | 用户要的就是「`[ ]` / `[x]` 都显示出来」 |
| 用 `listItem.checkbox` 判定勾没勾 | 只用它判「这一行是不是任务项」；勾没勾**读源码那三个字符** | cmark-gfm 那句 `strstr(整行, "[x]")` 会错报，见 `doc/bugHistory.md` 第 12 条 |

### 现在的渲染结果

`- [ ] 买牛奶` 渲染成（按显示顺序）：

| 文本流片段 | 挂的属性 | 说明 |
|---|---|---|
| `- ` | `.markerAttributes`（浅灰）+ `.markdownSyntaxMarker` | 源码本身；任务项**不画圆点** |
| 座位（透明 attachment） | `.markdownCheckboxSeat` = `CheckboxInfo`（**故意不带** `.markdownSyntaxMarker`） | 纯装饰、不消耗源码；宽度 = 方框边长 + 两侧间距 |
| `[ ] ` | `.markdownCheckbox` = `CheckboxInfo`（浅灰） | 源码本身，照常显示 |
| `买牛奶` | 正文 | |

按钮由 `MarkdownTextView.positionCheckboxes()` 摆在**座位矩形正中**。
开关是 `MarkdownTheme.taskList.coversCheckboxLiteral`：默认 `false` 走上面这条路；
改成 `true` 就退回「按钮盖住 `[x]`」的老样子（渲染层那时**不插座位**）。

### 两处容易踩的

1. **座位走的是 `decorationAttachment`**（`sourceStart = -1`）：复制时跳过，所以
   「全选复制 === 源文件」不受影响 —— 这条不变量有测试盯着（`testTaskListSelectAllCopiesSource`）。
2. **悬挂缩进用「最宽字面量」算出来的定值**（`MarkupToAttributedRenderer.taskListMarkerWidth`）。
   按当前字面量算能让单项内部严丝合缝，但 `[ ]` 和 `[x]` 的字宽差约 7pt，
   于是勾上的项和没勾的项第二行会各缩各的 —— 整列看着更乱，所以取了定值。
3. **座位不能带 `.markdownSyntaxMarker`**（2026-09-18 修的，别「统一」回去）。
   `- ` 和 `[ ] ` 是**两段独立**的语法标记，座位是它们之间的**边界**。
   座位一旦也带上这个属性，两段就被粘成一段连续标记 —— 退格规则是「删到标记里就整段一起删」，
   于是光标停在 `]` 右边按一下删除键，扩展范围会跨过座位把 `- [ ] ` 整段吃掉
   （实测源码从 `- [ ] 未完成的项` 变成 `未完成的项`）。
   同理，`MarkdownDocumentStore.expandedSyntaxMarkerRange` 里也要**遇到座位就停**，
   并且起点落在座位上时先往后挪一格（座位不占源码，直接删它算出的范围是空的 = 按了没反应）。
   来龙去脉见 `doc/bugHistory.md` 第 14 条，测试在 `MarkdownEditorHy4Tests/TaskListBackspaceTests.swift`。

### 任务项里的退格行为（修完之后的样子）

| 光标位置 | 源码变化 | 说明 |
|---|---|---|
| `]` 右边 | `- [ ] 未完成的项` → `- 未完成的项` | 只删复选框那几个字符，列表标记留着 |
| 座位上 | 同上 | 座位算它右边那一段的 |
| `- ` 里 | `- [ ] 未完成的项` → `[ ] 未完成的项` | 整段 `- ` 走掉，降级成普通段落 |

### 顺带一提：还没接线的两条

`1. [ ] 有序任务项` 和 `> - [ ] 引用块里的任务项` **没有复选框** ——
`appendTaskListMarker` 只在**无序列表**分支被调用（有序列表走的是直接显示 `1. ` 的分支）。
这是渲染入口没接线，不是 bug。
