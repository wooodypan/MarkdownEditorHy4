这份文档给没跑过测试的人看。读完你会做三件事，把本项目的测试全部跑一遍，看懂屏幕上的红绿标记，再查出一份代码覆盖率报告。最容易卡住的地方是选运行目的地，这个项目习惯用 Mac Catalyst 跑，目的地选 Mac 系就很顺，不用开 iOS 模拟器。

## 先看这个项目有多少测试

数了一下真实的文件。`MarkdownEditorHy4Tests` 目录里有 41 个测试文件，一共 582 个以 `func test` 开头的测试方法。`MarkdownEditorHy4UITests` 目录里只有 3 个方法，全部是 Xcode 新建工程时自带的示例，没有一个真的去点界面。

文件名就是各块测试守的行为。`MarkdownQuoteSpacingTests` 管引用块的段距，`DocumentRenameTests` 管重命名文档，`HTMLToMarkdownConverterTests` 密度最高，一个文件写了 43 个方法。

## 什么是单元测试

单元指一小块能单独检验的代码，一个函数或者一个类的行为。单元测试就是把"给它这个输入，它必须给我那个结果"写成代码，让机器自己去跑、自己去比，对不上就报错。它不需要把整个 App 界面打开给人看，也不需要人拿手指点。

看一段项目里的真代码，出自 `MarkdownQuoteSpacingTests.swift`。

```swift
func testWrappedLinesInsideQuoteHaveNoParagraphSpacing() {
    let (text, _) = render(markdown)
    let runs = quoteStyles(in: text)

    let first = pick("CCC", from: runs)
    XCTAssertEqual(first?.paragraphSpacing, 0, "引用里同一段话的第一行下面不该留段距")
}
```

`markdown` 是文件开头写死的一段示例文本，里面有以 `>` 开头的引用行。`render` 把这段文本交给应用内部的渲染器，得到带排版属性的富文本。`pick` 在结果里找到包含 "CCC" 那一行的段落样式。最后一行 `XCTAssertEqual` 检查这一行算出来的段后距，值等于 0 测试就通过，值成了别的就失败，屏幕上标红，并显示那句中文提示"引用里同一段话的第一行下面不该留段距"。提示是作者故意写的，目的是让半年后看到失败的人一眼明白坏的是什么事。

顺带注意文件顶部的 `@testable import MarkdownEditorHy4`。`@testable` 让测试代码能伸进应用内部平时不对外公开的部分，直接调用内部类，不然很多细节根本测不到。

为什么要把它写成测试而不是每次肉眼检查。引用块里同一段话折行时，行与行之间曾经多出 12 点的段距，整块引用看着散架，这个差异肉眼很难每次都盯住，而且下次有人改渲染代码很容易让它复发。写成测试之后，改完代码跑一遍，坏了立刻报红。

## 什么是 UI 测试

UI 测试扮演的是人。程序启动 App，替你去点按钮、往输入框打字，再检查界面有没有按预期变化。代码长这样，也出自本项目。

```swift
let app = XCUIApplication()
app.launch()
```

本项目的 UI 测试就停在启动这一步，后面没有操作。

两者对比着看，分工就清楚了。单元测试像把发动机拆开量零件，快，几百个测试几秒钟跑完，哪个零件不合格说得很准。UI 测试像验收整车，慢，跑一个测试要把 App 完整启动等界面出来，失败时原因常含糊，按钮没摆对还是逻辑本身坏了，得查。本项目现在的样子正合这个分工，渲染细节全压在单元测试上，UI 测试留着出厂的空壳。

## 什么是代码覆盖率

覆盖率是测试跑起来时，实际执行过的代码占全部代码的比例。假设某个文件有 100 行，测试运行期间走到了其中 70 行，这个文件的行覆盖率就是 70%。没被调用的函数、走了另一条分支的代码，一行都不会被执行，它们算在分母里，不算在分子里。

这个数要两头看。覆盖率低，说明有一大片代码改了也没人会发现，要补测试时优先补那里。覆盖率高也不等于对，一个测试可以把函数跑一遍却不对结果作任何检查，函数照样算覆盖到了。覆盖率回答"测试摸到了多少代码"，"有多少代码被认真测过"它不回答。

## 怎么跑这个项目的单元测试

Xcode 里跑。打开 `MarkdownEditorHy4.xcodeproj`，顶部 scheme 选 `MarkdownEditorHy4`，目的地选 Mac 系（比如 My Mac (Designed for iPad)，与项目平时用 Catalyst 的习惯一致），然后菜单 Product → Test，快捷键 ⌘U。第一次跑要拉取 SwiftSoup、cmark-gfm、SwiftMath 等五个包的依赖，再把整个工程编译一遍，花几分钟正常。

结果在左侧最右边一列导航器的报告页（Report Navigator，图标像对话气泡）。点开最近一次 Test，能看到按测试包、类、方法分组的通过失败情况。点一个失败的测试，Xcode 直接跳到出问题的那一行，旁边显示作者写的失败提示。

命令行跑。在项目目录打开终端，粘贴这段。

```bash
xcodebuild test \
  -scheme MarkdownEditorHy4 \
  -destination 'platform=macOS,variant=Mac Catalyst' \
  -only-testing:MarkdownEditorHy4Tests \
  -enableCodeCoverage YES \
  -resultBundlePath ./build/unit-coverage.xcresult
```

三个参数值得解释。`-only-testing:MarkdownEditorHy4Tests` 只跑单元测试包，把两个会真启动 App 的 UI 测试跳过。`-enableCodeCoverage YES` 打开覆盖率统计，默认是关的。`-resultBundlePath` 指定结果存哪，这个路径如果已经存在，命令会直接报错，重跑前要换一个名字或者删掉旧的。

想在 Xcode 里也跳过 UI 测试，菜单 Product → Scheme → Edit Scheme → Test，把列表里 `MarkdownEditorHy4UITests` 的勾去掉即可。

## 覆盖率报告怎么看

两种看法都要求先跑过一次带覆盖率开关的测试。

图形界面里，报告导航器点开最近一次 Test，上方有个 Coverage 标签页，按 Target、文件列出百分比、执行次数和命中次数。点文件名会跳进源码，行号左边出现小格子，绿格表示测试跑过这行，红格表示从没跑到，红得越深越没人碰。文件整体和单个函数的百分比也标在左栏。要是没看到这些格子，编辑器底部调试条里点 Code Coverage 把它调出来。

命令行用刚才存的 `.xcresult` 文件。

```bash
xcrun xccov view --report ./build/unit-coverage.xcresult
```

它按文件逐行输出覆盖率，从低到高排。想细看某个文件里哪个函数没被执行，加 `--file`。

```bash
xcrun xccov view --file MarkdownEditor/Rendering/MarkupToAttributedRenderer.swift ./build/unit-coverage.xcresult
```

## 几个常见卡点

依赖拉不下来导致编译失败。首次打开要等包解析完，网络不顺时菜单 File → Packages → Resolve Package Versions 重试一次。

目的地选了 iPhone 模拟器，跑得慢还起不来窗口。按项目习惯换回 Mac Catalyst 目的地。

签名错误。留着完整的报错文字，找负责证书和描述文件的人处理，不要自己乱改签名设置。

某个测试突然失败。先看失败提示再动手，判断是被测代码真的坏了，还是测试的期望过时了。渲染相关的测试变红，多半是有人刚改了排版参数，此时该改代码或者确认后更新测试，而不是删测试了事。

## 这个项目的测试习惯

本项目改渲染行为时会补一个对应的测试，测试文件按行为起名，`MarkdownQuoteSpacingTests` 守引用块段距就是这么来的。以后你改了渲染代码，照这个样子写一个小测试，把想守住的现象用一句 `XAssertEqual` 断住，这个 bug 就很难再回来。
